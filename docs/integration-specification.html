Integration Specification

ขอบเขตการเชื่อมต่อ ระบบต้นทาง–ปลายทาง วิธีรับส่งข้อมูล และความถี่ในการเชื่อมต่อ ของ Sony Badge Pilot ตามที่โค้ดเรียกจริง

  • ขอบเขต
  • ต้นทาง–ปลายทาง
  • สัญญาข้อมูล
  • ความถี่

ขอบเขตการเชื่อมต่อ (Scope)

ระบบนี้เป็น synchronous request/response ไม่มี message queue, webhook เข้า, หรือ batch job การเชื่อมต่อรันไทม์มีสี่เส้นทางหลัก

อยู่ในขอบเขต LINE LIFF (ไคลเอนต์), LINE ID token verify (เซิร์ฟเวอร์), Sony warranty APIM, MySQL กฎเหรียญ
นอกขอบเขต API ผู้ใช้กดไปเว็บ Sony (บัญชี / ลงทะเบียน / microsite) เป็นการนำทางเบราว์เซอร์ แอปไม่ส่ง LINE ID ติด query
ไม่เชื่อมต่อ ไม่มี CMS, ไม่เรียก Facebook Graph จากเซิร์ฟเวอร์, ไม่มี webhook จาก Sony เมื่อลูกค้าลงทะเบียนสินค้าใหม่
โหมด SONY_PRODUCT_API_MODE=mock ไม่เรียก APIM ใช้ข้อมูลจำลองในโปรเซส ใช้ได้ตามที่ตั้งค่า (local / หรือ UAT ที่ยังเป็น mock)

วิธีรับส่งข้อมูล (Contracts)

INT-01 LINE LIFF

ไลบรารี @line/liff ใช้ NEXT_PUBLIC_LIFF_ID เรียก liff.init, liff.getIDToken(), liff.getProfile() ต้องอยู่ภายใน LINE client

INT-03 LINE verify

ค่าเริ่มต้น URL: https://api.line.me/oauth2/v2.1/verify (ปรับได้ด้วย LINE_VERIFY_ID_TOKEN_URL) 

POST
Content-Type: application/x-www-form-urlencoded

id_token=<LIFF ID token>
client_id=<LINE_CHANNEL_ID>

แอปใช้ sub เป็น LINE user ID และตรวจ aud ให้ตรงช่อง ไม่ persist ID token

INT-02 Mini App ↔ Omelet

API Method ข้อมูลเข้า ข้อมูลออก
/api/line-session POST JSON { "idToken": "..." } { "ok": true } + cookie sony_line_session
/api/my-badges เป็นต้น GET query lineuuid, บางเส้นมี locale JSON เหรียญ/สินค้า/ภารกิจ; ไม่มีตัวตนถ้าไม่ส่ง lineuuid (ชั้นล็อก)
/api/customer-products GET cookie session (เส้นทาง diagnostic) shelf แบบตัด PII; อาจมี cache hint

INT-04 Sony warranty APIM

URL มาจาก SONY_PRODUCT_API_BASE_URL ตัวอย่างสภาพแวดล้อมพัฒนา: https://apim-rcap-dev.azure-api.net/mysony-api/QueryWarrantyMySonyByLine 

POST
Accept: application/json
Content-Type: application/json
Ocp-Apim-Subscription-Key: <server-only secret>

{
  "countryCode": "th",
  "lineId": "<LINE user ID>"
}

รูปแบบตอบที่แอปแปลงใช้:

{
  "prodDetails": [
    {
      "lineId": "U...",
      "serialNumber": "1000003",
      "modelName": "ZV-E10M2/BQ AP2",
      "registrationDate": "2026-03-25",
      "warrantyExpiryDate": "2027-06-23"
    }
  ]
}

แอป map modelName เป็น SKU ภายใน HTTP 404 ตีความเป็นลูกค้าไม่พบ cache: "no-store" ทุกครั้ง

INT-05 MySQL

เชื่อมด้วย DATABASE_URL (โปรโตคอล mysql:) UAT ต้องเปิด TLS อ่าน badge_rules และตารางลูก ไม่ได้เก็บ ownership ของลูกค้า

INT-06 เว็บ Sony

NEXT_PUBLIC_ACCOUNT_URL, NEXT_PUBLIC_REGISTER_PRODUCT_URL, และลิงก์ inquiry ไป https://www.sony.co.th/microsite/digital-badge/ ไม่มี request body จากเซิร์ฟเวอร์แอป

ความถี่ในการเชื่อมต่อ (Frequency)

ไม่มี scheduler — เกิดตามการกระทำของผู้ใช้
Integration ทริกเกอร์ ความถี่โดยประมาณ Cache / จำกัดซ้ำ
INT-01 LIFF โหลด Mini App / LineSessionProvider ครั้งต่อแท็บจนกว่า session ในหน้าพร้อม init LIFF ใช้ promise รวมในโมดูล; โปรไฟล์เก็บใน sessionStorage ของแท็บ
INT-03 LINE verify POST /api/line-session ครั้งเมื่อสร้างหรือต่ออายุ session จาก LIFF cookie อายุ 1 ชั่วโมง ไม่ได้ refresh อัตโนมัติเป็นพื้นหลัง
INT-04 Sony APIM ทุกครั้งที่ /api/my-* มี lineuuid (และเส้นทาง customer-products แบบ cache miss) ต่อหน้า / ต่อการ fetch ของไคลเอนต์ ไม่มี polling ไคลเอนต์ my-* ใช้ cache: "no-store" จึงเรียก Sony ใหม่ทุกโหลด
INT-05 MySQL อ่านกฎ คู่กับคำนวณเหรียญ ต่อ request ที่ต้องใช้กฎ cache ในโปรเซส 60 วินาที ตาม badge_rules_version
INT-05 เขียน log เส้นทาง getBadgeResultForLineUuid (legacy shelf) ต่อครั้งที่คำนวณเส้นนั้น หน้า Mini App หลักไม่เขียนตารางนี้
INT-06 เว็บ Sony ผู้ใช้กดปุ่ม ตามการใช้งาน ไม่ใช่ตามรอบเวลา —
ไม่มี inbound webhook เมื่อลูกค้าเพิ่งลงทะเบียนสินค้าที่ Sony เหรียญจะอัปเดตเมื่อผู้ใช้เปิด Mini App แล้วแอปเรียก warranty API รอบใหม่
