Error Handling & Retry Flow

วิธีจัดการเมื่อเชื่อมต่อไม่สำเร็จ การ Retry และการบันทึก Log ของ LINE, Sony APIM, MySQL และ Mini App API

สถานะปัจจุบัน: ไม่มีการ retry / backoff ในแอป แต่ละการเรียกภายนอกเป็นครั้งเดียว (single attempt) ความล้มเหลวถูก map เป็นรหัสปลอดภัย หรือแสดงแคตตาล็อกล็อก

  • นโยบาย (Policy)
  • Retry
  • ลำดับเมื่อล้มเหลว (Error flow)
  • รหัสข้อผิดพลาด (Error codes)
  • พฤติกรรมต่อ API
  • การบันทึก Log
  • ช่องว่าง (Gaps)

นโยบาย (Policy)

ไม่เปิดเผยรายละเอียดภายใน JSON สาธารณะใช้ toSafeError ข้อความทั่วไป เช่น “temporarily unavailable” ไม่ส่ง stack, token, หรือ serial
ไม่ retry อัตโนมัติ ไม่มี loop, ไม่มี exponential backoff, ไม่มี queue ผู้ใช้ต้องโหลดหน้าใหม่ หรือเข้าหน้าอีกครั้ง
สองแบบการตอบผู้ใช้ /api/customer-products ส่ง HTTP error · /api/my-products และรายการภารกิจส่วนใหญ่ พยายามคืนหน้าล็อกแทน

การเชื่อมต่อที่อาจล้ม: LIFF init, LINE verify ID token, Sony QueryWarrantyMySonyByLine, MySQL กฎเหรียญ ไม่มี webhook / job ที่ retry ภายหลัง

Retry

สิ่งที่มีและไม่มี (What exists)
ชั้น (Layer) Retry ในโค้ด พฤติกรรมจริง (Actual behavior)
Sony APIM fetch ไม่มี ครั้งเดียว · ไม่มี AbortSignal · ไม่มี timeout ในแอป
LINE verify ID token ไม่มี HTTP ไม่สำเร็จ → UNAUTHORIZED ทันที
LIFF liff.init รีเซ็ต promise เมื่อล้ม ครั้งถัดไปที่เรียก getCurrentLiffClient จะ init ใหม่ ไม่ใช่ retry ภายในครั้งเดียว
ไคลเอนต์ Mini App ไม่มีปุ่ม retry อัตโนมัติ useLineSessionData fetch ครั้งเดียวต่อ lineUuid · ยกเลิกด้วย AbortController เมื่อ unmount
MySQL pool ไม่ใช่ retry ของธุรกิจ waitForConnections: true, connectionLimit: 10 คิวรอ connection ในพูล ไม่ลอง query ซ้ำเมื่อ query ล้ม
เขียน badge_calculation_logs ไม่ retry .catch(() => undefined) ทิ้งความล้มเหลวของการเขียน log เพื่อไม่ให้บังหน้าผลคำนวณ
คำว่า “Please try again later” ใน UNKNOWN_ERROR เป็นข้อความผู้ใช้ ไม่ได้หมายความว่าเซิร์ฟเวอร์จะลองใหม่ให้

ลำดับเมื่อเชื่อมต่อไม่สำเร็จ (Error flow)

Sony warranty (INT-04)

getCustomerProducts(lineId)
  │
  ├─ ไม่มี subscription key → SONY_PRODUCT_API_ERROR
  ├─ HTTP 404              → CUSTOMER_NOT_FOUND
  ├─ HTTP อื่นที่ไม่ใช่ 2xx → SONY_PRODUCT_API_ERROR
  ├─ payload ไม่ครบ        → SONY_PRODUCT_API_ERROR
  └─ เครือข่ายค้าง/timeout ของแพลตฟอร์ม
                           → ไม่มีรหัส TIMEOUT (กลายเป็น UNKNOWN หรือ API error)

เส้นทางคำนวณเหรียญแบบมี log

เฉพาะ getBadgeResultForLineUuid (ใช้โดย GET /api/customer-products) 

try Sony + MySQL rules + calculate
  ├─ สำเร็จ → writeBadgeCalculationLog (hash, นับ SKU, สรุปเหรียญ)
  │           .catch เงียบถ้า DB เขียนไม่ได้
  └─ ล้ม    → writeBadgeCalculationLog (error_code, error_message ที่ปลอดภัย)
             แล้ว throw ต่อ → HTTP 401 / 404 / 500

เส้นทาง Mini App (my-*)

GET /api/my-products | /api/my-missions
  ├─ ไม่มี lineuuid     → แคตตาล็อกล็อก (ไม่เรียก Sony)
  ├─ Sony/DB ล้ม         → พยายามแคตตาล็อกล็อก HTTP 200
  └─ โหลดกฎล็อกไม่ได้   → 500 { code, message }

GET /api/my-badges
  └─ ล้ม → 500 ทันที (ไม่มี fallback ล็อกใน route นี้)
           และ console.log locale + lineuuid ดิบ

GET /api/my-products/[id] | /api/my-missions/[id]
  ├─ ไม่พบรหัสในกฎ      → 404 NOT_FOUND
  └─ Sony ล้ม (detail)   → mission มี fallback ล็อก; product detail ส่ง 500

LINE session

LIFF getIDToken → POST /api/line-session
  ├─ ไม่มี idToken        → 400 MISSING_ID_TOKEN
  ├─ LINE verify ไม่ผ่าน  → 401 UNAUTHORIZED
  └─ ข้อผิดพลาดอื่น       → 500 UNKNOWN_ERROR
ไคลเอนต์: response ไม่ ok → throw "LINE session could not be verified."
getLineProfile จาก LIFF ล้ม → คืน null (ไม่บล็อกเซสชัน)

รหัสข้อผิดพลาด (Error codes)

รหัสที่ไคลเอนต์อาจเห็น (Public codes)
code HTTP โดยทั่วไป สาเหตุ (Cause) ข้อความปลอดภัย (safeMessage)
MISSING_ID_TOKEN 400 body ไม่มี idToken LINE ID token is required.
UNAUTHORIZED 401 ไม่มีคุกกี้เซสชัน หรือ LINE verify ล้ม LINE session is required. (หรือข้อความ verify)
CUSTOMER_NOT_FOUND 404 Sony HTTP 404 หรือ mock ไม่รู้จัก lineuuid Customer profile was not found.
NOT_FOUND 404 productId / missionId ไม่อยู่ในกฎ หรือยังไม่ปลดล็อก Product / Mission badge not found.
SONY_PRODUCT_API_ERROR 500 APIM ไม่สำเร็จ หรือ payload ไม่ถูกต้อง Badge data is temporarily unavailable.
UNKNOWN_ERROR 500 error ที่ไม่มี code + safeMessage Something went wrong. Please try again later.

toSafeError คืนรหัสต้นทางเฉพาะเมื่อ object มีทั้ง code และ safeMessage เป็นสตริง Error ของ MySQL ดิบจะกลายเป็น UNKNOWN_ERROR

พฤติกรรมต่อพื้นผิว API (Per-surface behavior)

เมื่อ Sony หรือฐานข้อมูลล้มเหลว
Endpoint ผู้ใช้เห็น (User-facing) เขียน calculation log
GET /api/customer-products JSON error + HTTP 404/500 ใช่ (hash เท่านั้น)
GET /api/my-products, GET /api/my-missions แคตตาล็อกล็อก HTTP 200 ถ้าโหลดกฎได้ ไม่
GET /api/my-badges 500 JSON error · หน้าบ้านแสดงวิวว่าง ไม่
GET /api/health เสมอ { status: "ok" } ไม่ตรวจ Sony/DB

หน้า Mini App ไม่มีปุ่ม “ลองใหม่” แยก การโหลดใหม่ของ LIFF หรือเปลี่ยน lineUuid จะยิง fetch อีกครั้งหนึ่ง

ตำแหน่ง สิ่งที่พิมพ์ ความเสี่ยง (Risk)

2. ตาราง badge_calculation_logs

เขียนแบบ fire-and-forget จาก getBadgeResultForLineUuid ถ้าไม่มี DATABASE_URL จะข้าม

คอลัมน์ที่เก็บ (Stored columns)
คอลัมน์ เนื้อหา
customer_line_uuid_hash HMAC-SHA256 ของ lineuuid ด้วย LOG_HASH_SECRET หรือ fallback APP_SESSION_SECRET ไม่เก็บ LINE ID ดิบ
source_sku_count จำนวนสินค้าจาก Sony (เมื่อล้มเป็น 0)
matched_sku_count ผลรวม matchedCount ของเหรียญที่คำนวณ
earned_badges_json อาร์เรย์ { code, status, matchedCount } เมื่อล้มเป็น []
error_code / error_message จาก toSafeError เมื่อ catch สำเร็จเป็น NULL
created_at timestamp · มี index เรียงใหม่ก่อน
Mini App ที่ใช้ getBadgeExperienceForLineUuid ไม่เขียนแถวนี้ การเปิด my-badges / my-products จึงไม่เหลือประวัติ error ในตาราง แม้ Sony จะล้ม

ไม่มี job ลบ log ตามอายุ (retention) การลบต้องทำนอกแอป

3. สิ่งที่ไม่ถูก log

  • ไม่ส่ง log ไป SIEM / Application Insights จากโค้ดแอปโดยตรง
  • ไม่เก็บ serial, modelName, ID token ในตาราง log
  • /api/customer-products ตัด serial ออกจาก JSON แสดงผล แต่ debug trace แบบ local ยังมีชุดข้อมูลที่ redact แล้ว

ช่องว่าง (Gaps)

  • กำหนด timeout + retry นโยบายชัด (เช่น 1 ครั้งเมื่อ 502/503/timeout จาก APIM) และรหัส TIMEOUT แยกจาก SONY_PRODUCT_API_ERROR
  • หยุดพิมพ์ lineuuid ดิบใน console ให้ใช้ hashLineUuid
  • เขียน calculation log จากเส้นทาง my-* ด้วย หรือรวมให้เหลือแหล่งเดียว
  • ทำ health check ที่ตรวจ MySQL / APIM แยกจาก liveness ของโปรเซส
  • ปุ่มหรือข้อความ “ลองใหม่” บน Mini App เมื่อเป็น 500 จริง (ตอนนี้ my-products อาจดูเหมือน “ยังไม่มีเหรียญ” ทั้งที่ Sony ล่ม)
  • GET /api/my-missions มีโค้ดหลัง return ใน catch ที่ไม่ถูกเรียก fallback 500 เมื่อโหลดแคตตาล็อกล็อกไม่ได้จึงไม่ทำงานใน route นี้
