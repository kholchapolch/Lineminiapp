Security & PDPA Technical Document

วิธีที่ Sony Badge Pilot จัดเก็บ ประมวลผล ส่งต่อ และป้องกันข้อมูลส่วนบุคคล (how the Mini App stores, processes, transfers, and protects personal data)

เอกสารนี้เป็นคำอธิบายเทคนิคจากโค้ดปัจจุบัน ไม่ใช่ความเห็นทางกฎหมาย และยังรอการยืนยันจาก Security / PDPA ของ Sony ห้ามวาง LINE ID, ซีเรียล, หรือข้อมูลลูกค้าลง GitHub issue, screenshot, หรือแชท

รายการข้อมูลส่วนบุคคล (Personal data inventory)

ระบบนี้ไม่เป็นแหล่งข้อมูลหลักของลูกค้า ข้อมูลการถือครองสินค้าอยู่ที่ Sony warranty API Mini App ดึงมาคำนวณเหรียญตอน request

ข้อมูลที่เกี่ยวกับบุคคล
ข้อมูล (Data) แหล่งที่มา (Source) ใช้เพื่อ (Purpose) Persist ใน MySQL หรือไม่
LINE user ID (lineuuid / sub) LIFF ID token และ liff.getProfile() ระบุผู้ใช้ แล้วเรียก warranty API ไม่เก็บค่าดิบ — log เก็บแค่ HMAC/SHA-256 hash
LINE display name, picture URL LIFF profile บนเบราว์เซอร์ แสดงโปรไฟล์บนหน้า my-badges ไม่
LINE ID token LIFF getIDToken() ยืนยันตัวตนกับ LINE แล้วทิ้ง ไม่ — ส่งไป LINE ครั้งเดียวตอนสร้าง session
Model name / SKU, วันลงทะเบียน, หมายเลขซีเรียล Sony APIM QueryWarrantyMySonyByLine คำนวณเหรียญ และแสดงบนหน้ารายละเอียดสินค้าที่ปลดล็อกแล้ว ไม่ — ดึงใหม่ทุกครั้งที่โหลดหน้า
สรุปเหรียญที่ได้ คำนวณในแอป log การทำงานของเส้นทาง legacy shelf ใช่ ใน badge_calculation_logs.earned_badges_json (รหัสเหรียญ ไม่มีซีเรียล)
ไม่ใช่ข้อมูลส่วนบุคคลของลูกค้า กฎเหรียญ, รายการ SKU ในเงื่อนไข, รูปเหรียญ, URL สินค้า เป็นข้อมูลแคมเปญ ไม่ผูกกับบุคคล
วันหมดประกัน API อาจส่ง warrantyExpiryDate ตัวแปลงปัจจุบันไม่เก็บและไม่แสดงค่านี้

การเก็บรวบรวม (Collection)

  1. ผู้ใช้เปิด Mini App ใน LINE ไคลเอนต์ init LIFF แล้วส่ง ID token ไป POST /api/line-session
  2. เซิร์ฟเวอร์ยืนยัน token กับ LINE (LINE_VERIFY_ID_TOKEN_URL) แล้วอ่าน sub เป็น LINE user ID
  3. เซิร์ฟเวอร์เรียก Sony warranty API ด้วย lineId และ countryCode รับ prodDetails (model, serial, registration date)
  4. ไคลเอนต์เก็บ LINE user ID ใน sessionStorage และใส่เป็น query lineuuid เมื่อเรียก /api/my-*
หน้าแชร์สาธารณะ /share/product/... และ /share/mission/... โหลดแค่ชื่อเหรียญและรูปจากกฎ ไม่ดึงข้อมูลลูกค้า

ที่จัดเก็บ (Storage locations)

ที่ข้อมูลพักอยู่
ที่เก็บ สิ่งที่อยู่ อายุโดยประมาณ เข้าถึงจาก JS ได้หรือไม่
Cookie sony_line_session payload base64 ของ { lineuuid, expiresAt } + HMAC-SHA256 1 ชั่วโมง (Max-Age=3600) ไม่ได้ — HttpOnly, SameSite=Lax, Secure นอก local
sessionStorage คีย์ sony_line_uuid LINE user ID ค่าดิบ จนปิดแท็บ ได้ — สคริปต์ในหน้าเดียวกันอ่านได้
localStorage คีย์ sonyBadgeCache:v1 ผลเหรียญของเส้นทาง legacy /badges + cache key ที่เป็น hash จนกว่าจะ invalidate ด้วย badge_rules_version ได้ — ใช้เฉพาะ diagnostic shelf ไม่ใช่หน้า my-badges
MySQL badge_calculation_logs HMAC ของ LINE ID, จำนวน SKU, JSON สรุปรหัสเหรียญ ไม่มี job ลบอัตโนมัติในโค้ด —
หน่วยความจำเซิร์ฟเวอร์ กฎเหรียญ cache 60 วินาที ไม่ใช่ข้อมูลลูกค้า TTL สั้น —
หน้า my-product ที่ปลดล็อกแล้ว ซีเรียลและวันลงทะเบียนใน JSON ของ API แค่ตอนแสดงผล ไม่ persist ที่แอป ได้ใน DOM/network ของผู้ใช้นั้น
หน้า Mini App ปัจจุบัน (/api/my-*) เรียกแบบ cache: "no-store" ไม่เขียนผลลัพธ์ลง localStorage

การประมวลผล (Processing)

  1. Normalize SKU แล้วเทียบกับ Eligible Product ของกฎ
  2. นับรุ่นไม่ซ้ำ ภายในหน้าต่าง registration_start/end ถ้ามี
  3. เทียบ matched count กับ Threshold / Tier
  4. ส่งผลลัพธ์ที่จำเป็นต่อ UI — ซีเรียลออกเฉพาะหน้ารายละเอียดสินค้าที่ปลดล็อกแล้ว

เส้นทาง legacy /api/customer-products ตัด payload ก่อนส่งเบราว์เซอร์: ไม่ใส่ lineuuid, ซีเรียล, หรือรายการสินค้าดิบ โหมด debug ใน production ถูกปิด แผง debug JSON แสดงแค่ว่ามีฟิลด์หรือไม่ ไม่แสดงค่าดิบ

การส่งต่อ (Transfer / disclosure)

ผู้รับข้อมูลภายนอกแอป
ผู้รับ ช่องทาง ข้อมูลที่ส่ง ทิศทาง
LINE POST verify ID token ID token + channel ID แอป → LINE เพื่อยืนยันตัวตน
Sony APIM (warranty) POST พร้อม Ocp-Apim-Subscription-Key countryCode, lineId แอป → Sony แล้วรับรายการสินค้ากลับ
เบราว์เซอร์ของผู้ใช้ HTTPS ไปหน้า Mini App และ /api/my-* โปรไฟล์ที่แสดง, สถานะเหรียญ, ซีเรียลบนหน้ารายละเอียดสินค้า แอป → อุปกรณ์ของผู้ใช้
Facebook / OG crawler หน้า /share/... สาธารณะ ชื่อเหรียญและรูปจากกฎเท่านั้น ไม่มีข้อมูลลูกค้า
ลิงก์ภายนอก (ลงทะเบียน / บัญชี Sony) NEXT_PUBLIC_ACCOUNT_URL และ URL สินค้า ผู้ใช้เดินทางไปโดเมน Sony — แอปนี้ไม่ส่ง LINE ID ติดไปใน query การนำทางของผู้ใช้

Azure App Service และ Azure MySQL อยู่ฝั่งโครงสร้างพื้นฐาน UAT การเชื่อม DB ใช้ TLS เมื่อตั้ง DATABASE_SSL=true และยังตรวจใบรับรอง

การป้องกัน (Protection controls)

มาตรการในโค้ดปัจจุบัน
ชั้น (Layer) มาตรการ รายละเอียด
ความลับ Server-only secrets DATABASE_URL, APP_SESSION_SECRET, LOG_HASH_SECRET, SONY_PRODUCT_API_SUBSCRIPTION_KEY ห้ามใส่ NEXT_PUBLIC_*
Session Signed HttpOnly cookie HMAC-SHA256, ตรวจด้วย timingSafeEqual, TTL 1 ชั่วโมง ใช้กับ /entry และ /api/customer-products
ทางเข้า Origin / Referer guard /entry ตรวจ ALLOWED_ORIGINS และ ALLOWED_REFERRERS
LIFF ต้องเปิดใน LINE client สร้าง session จาก ID token เฉพาะเมื่อ liff.isInClient()
Log Hash LINE ID hashLineUuid ใช้ HMAC-SHA256 เมื่อมี LOG_HASH_SECRET หรือ APP_SESSION_SECRET
API error Safe error message toSafeError ไม่ส่ง stack หรือข้อความภายในให้ไคลเอนต์
Debug ปิดใน production ?debug=1 และ NEXT_PUBLIC_DEBUG_MOCK_JSON ใช้ไม่ได้เมื่อ APP_ENV=production
Cache เบราว์เซอร์ (legacy) ไม่เก็บ SKU ดิบ คีย์ cache เป็น hash ของลูกค้า + hash ของชุด SKU + เวอร์ชันกฎ
ฐานข้อมูล TLS UAT ต้องเปิด SSL และไม่ปิด certificate verification

ความเสี่ยงที่ยังเหลือและข้อจำกัด (Residual risks)

จุดด้านล่างเป็นพฤติกรรมจริงในโค้ด ที่ทีม Security / PDPA ควรทราบ ยังไม่ถือว่าปิดความเสี่ยงแล้ว

หัวข้อ พฤติกรรมปัจจุบัน ผลต่อข้อมูลส่วนบุคคล
สองช่องทางระบุตัวตน Cookie ใช้กับ /api/customer-products แต่ /api/my-badges, /api/my-products, /api/my-missions รับ ?lineuuid= โดยไม่ตรวจ cookie ผู้ที่รู้ LINE user ID อาจเรียกดูผลเหรียญและซีเรียลของคนนั้นได้
Query string และ sessionStorage LINE user ID ค่าดิบอยู่ใน URL ของ XHR และใน sessionStorage อาจโผล่ใน proxy log, analytics, หรือสคริปต์ที่รันในหน้า
console.log /api/my-badges, /api/my-missions, และ getCustomerProducts ยังพิมพ์ lineuuid ค่าดิบอาจเข้า App Service / container logs
Cookie payload LINE ID ใน cookie เป็น base64 ไม่ได้เข้ารหัส แค่เซ็น HMAC ผู้ที่อ่าน cookie จากเครือข่าย/ดิสก์เห็น LINE ID ได้ แม้แก้ค่าแล้วเซ็นไม่ผ่าน
Retention ของ log ไม่มีงานลบ badge_calculation_logs hash สะสมจนกว่าจะลบด้วยปฏิบัติการ
Fallback session secret ถ้าไม่ตั้ง APP_SESSION_SECRET local ใช้ค่าคงที่ในโค้ด ต้องมี secret จริงบน staging/production
จนกว่า Security / PDPA จะยืนยันแนวทาง ห้ามส่งออกข้อมูลลูกค้าจากระบบนี้ไปรายงาน ไฟล์ทดสอบ หรือเอกสารสาธารณะ และควรตั้ง LOG_HASH_SECRET คนละค่ากับ secret อื่นเมื่อเป็นไปได้

Authorization Fail /api/my-* ไม่ผูกกับ session cookie

Checklist ตามหัวข้อ

Authentication

ข้อตรวจ ผล หลักฐาน
ยืนยัน LINE ID token กับ LINE ไม่เชื่อ token จากไคลเอนต์อย่างเดียว Pass verifyLineIdToken เรียก api.line.me ตรวจ aud / sub / exp
LIFF ต้องรันใน LINE client Pass liff.isInClient() ก่อนสร้าง session
staging/production บังคับ LIFF ID, channel ID, session secret Pass loadAppConfig + config:check (secret ≥ 32 ตัว, LIFF ต้องเป็นของ channel)
หน้า Mini App หลักใช้ session ที่ verify แล้วเป็นตัวระบุตัวตน Fail /api/my-* อ่าน ?lineuuid= โดยไม่เรียก resolveAuthorizedLineUuid
Mock / demo identity ถูกจำกัดเฉพาะ local Pass /api/mock-session คืน 404 นอก local+mock; query demo บน customer-products เฉพาะ debug+mock

Authorization

ข้อตรวจ ผล หลักฐาน
ไม่มีหน้า admin ให้ลูกค้าแก้กฎ Pass ไม่มี CMS; กฎมาจาก seed
ลูกค้าเห็นแต่ข้อมูลของตนเอง Fail IDOR: ใส่ LINE user ID ของผู้อื่นใน query ของ /api/my-* แล้วได้เหรียญและซีเรียล
/entry จำกัดแหล่งที่มา Pass Origin/Referer ต้องอยู่ใน allowlist และต้องมี cookie
เส้นทาง legacy shelf ใช้ cookie Pass /api/customer-products ใช้ resolveAuthorizedLineUuid
หน้าแชร์ไม่เปิดข้อมูลลูกค้า Pass getPublicShareMeta อ่านแค่กฎและรูป

Encryption

ข้อตรวจ ผล หลักฐาน
UAT บังคับ HTTPS ของแอปและ URL ภายนอก Pass config:check ตรวจ https:; App Service HTTPS Only ตาม runbook
MySQL ใช้ TLS และยังตรวจใบรับรอง Pass rejectUnauthorized: true; deploy ต้องมี DATABASE_SSL
ความลับไม่ถูกใส่ NEXT_PUBLIC_* Pass APIM key, DB, session secret เป็น server-only
ข้อมูลระบุตัวตนใน cookie ถูกเข้ารหัส Partial HMAC-SHA256 ป้องกันการแก้ค่า แต่ payload เป็น base64 อ่าน LINE ID ได้ถ้าได้คุกกี้
ความลับใน Git Pass ไม่ commit .env*; UAT ใช้ environment secret

Logging

ข้อตรวจ ผล หลักฐาน
ตาราง log ไม่เก็บ LINE ID ดิบ Pass hashLineUuid HMAC-SHA256 เมื่อมี LOG_HASH_SECRET
ข้อความ error ถึงไคลเอนต์ไม่รั่วรายละเอียดภายใน Pass toSafeError
ไม่มี PII ใน stdout / App Service log Fail console.log({ lineuuid }) ใน my-badges, my-missions และ getCustomerProducts
Debug payload ไม่ส่งซีเรียลดิบใน production Pass debug ปิดเมื่อ APP_ENV=production; debug JSON ใช้ธง present

Session

ข้อตรวจ ผล หลักฐาน
Cookie เป็น HttpOnly, SameSite, มีอายุ Pass HttpOnly, SameSite=Lax, Max-Age=3600, Secure นอก local
ลายเซ็นกันการปลอมแปลง Pass HMAC-SHA256 + timingSafeEqual
ไม่เก็บ session ใน JS ที่อ่านได้ Fail sessionStorage.sony_line_uuid เก็บ LINE ID ดิบ และส่งต่อใน URL
ไม่มี fallback secret อ่อนบน staging Pass นอก local ต้องมี APP_SESSION_SECRET; ค่าคงที่ในโค้ดใช้แค่ local

API Security

ข้อตรวจ ผล หลักฐาน
SQL injection บน input จากผู้ใช้ Pass insert/log ใช้ parameterized execute; query กฎเป็น SQL คงที่
Rate limiting / abuse control Fail ไม่มีในแอป — เรียก Sony APIM ได้ตามปริมาณ request ของ Mini App API
Security headers (CSP, HSTS, X-Frame-Options) Partial แอปไม่ตั้ง CSP/frame options; HSTS พึ่ง HTTPS ของ Azure/IIS
CSRF บนการเปลี่ยนสถานะ Partial POST /api/line-session เป็น same-site จาก LIFF แต่ GET /api/my-* ใช้ตัวตนใน query จึงเสี่ยง IDOR มากกว่า CSRF แบบคลาสสิก
Endpoint อันตรายถูกล็อกนอก local Pass mock-session 404; debug ปิดใน production; NEXT_PUBLIC_DEBUG_MOCK_JSON ต้องเป็น false ตอน deploy
Health ไม่เปิดข้อมูลภายใน Pass {"status":"ok","runtime":"nodejs"}

Findings ที่ควรปิด

ID ความรุนแรง หัวข้อ รายละเอียด แนวทางแก้ (ไม่ลงมือในเอกสารนี้)
F1 High Authorization / IDOR /api/my-badges, /api/my-products, /api/my-missions เชื่อ lineuuid จาก query ใช้ resolveAuthorizedLineUuid จาก cookie เหมือน customer-products
F2 Medium Logging stdout ยังพิมพ์ LINE user ID ดิบตอน live warranty และบาง my-* API ลบ console.log หรือใช้ hashLineUuid
F3 Medium Session / PII in browser LINE ID อยู่ใน sessionStorage และ query string ของ XHR พึ่ง cookie อย่างเดียว ไม่ส่ง identity ใน URL
F4 Low Encryption at rest (cookie) cookie อ่าน LINE ID ได้ถ้าขโมยคุกกี้ เก็บแค่ opaque session id หรือเข้ารหัส payload
F5 Low API abuse ไม่มี rate limit ไปยัง Sony APIM จำกัดต่อ session / IP ที่ขอบแอปหรือ APIM
F6 Low Security headers next.config.mjs ไม่ใส่ CSP / clickjacking headers ตั้ง headers ที่ IIS หรือ Next

ช่องโหว่พื้นฐาน (Baseline vulns)

กลุ่ม ผลตรวจ หมายเหตุ
Injection (SQL) ไม่พบรูปแบบ query ต่อสตริงจากผู้ใช้ input จาก LINE/SKU ไม่ถูกต่อเป็น SQL ของกฎ
XSS ความเสี่ยงต่ำ ไม่พบ dangerouslySetInnerHTML รูปเหรียญมาจาก URL ใน DB — ผู้มีสิทธิ์ seed/DB ตั้ง URL ได้ ลูกค้าทั่วไปตั้งค่านี้ไม่ได้
SSRF ความเสี่ยงต่ำ warranty URL มาจาก env ไม่ใช่จากผู้ใช้
Secret exposure ควบคุมในรีโป มี console.log ของ subscription key ที่ถูก comment แล้วใน app-config.ts
Information disclosure บางจุด debug ปิดใน production getPublicDbSchema / debug tables มีได้เฉพาะโหมด debug health ไม่เปิดเวอร์ชันรายละเอียด
Broken access control พบ F1 เป็นช่องโหว่หลักของ Mini App API
Security misconfiguration บางจุด deploy check เข้มเรื่อง HTTPS/TLS/debug; แอปไม่มี CSP; workflow ไม่รัน npm audit
Open mock/debug in prod ถูกบล็อก mock-session และ debug flag
จุดที่ควรแก้ก่อนขยาย production ตามลำดับ: F1 (ผูก my-* กับ cookie) แล้ว F2–F3 (log และไม่ใส่ LINE ID ใน URL)

Data Flow Diagram

การส่งข้อมูลระหว่าง LINE, LIFF/Mini App, Omelet System และ Sony System ตามเส้นทางที่โค้ดปัจจุบันใช้จริง

  • รายการ data flow
  • ลำดับหลัก (Happy path)

ขอบเขตระบบ (System boundaries)

LINE LINE App, LIFF SDK, และ https://api.line.me/oauth2/v2.1/verify ให้ ID token, LINE user ID (sub), ชื่อและรูปโปรไฟล์
LIFF / Mini App หน้าเว็บที่รันใน LINE webview: my-badges, my-products, my-missions, share เก็บ sessionStorage และเรียก API ของ Omelet
Omelet System Next.js บน Azure App Service ของโดเมน Mini App: session, badge engine, API /api/* และ MySQL ที่เก็บกฎเหรียญ (ไม่เก็บสินค้าของลูกค้า)
Sony System Azure APIM warranty (QueryWarrantyMySonyByLine) และเว็บ Sony Thailand สำหรับบัญชี / ลงทะเบียน / หน้า digital-badge

แผนภาพบริบท (Context data flow)

ลูกศรทึบคือข้อมูลที่ระบบส่งใน happy path ของ Mini App ลูกศรประคือการนำทางผู้ใช้ไปเว็บ Sony โดยแอปไม่ส่ง LINE ID ติดไป

สี่เหลี่ยมมุมแหลม = ระบบภายนอก (LINE, Sony) มุมโค้ง = กระบวนการของแอป (Mini App, Omelet) สี่เหลี่ยมเปิด = ที่เก็บข้อมูล

รายการ data flow

หมายเลขบนแผนภาพ
# จาก ถึง ข้อมูล ช่องทาง
1 LINE LIFF / Mini App LIFF SDK, ID token, LINE user ID, ชื่อและรูปโปรไฟล์ liff.init, getIDToken(), getProfile()
2 LIFF / Mini App LINE คำขอ init / token / profile ต้องเปิดใน LINE client LIFF SDK
3 LIFF / Mini App Omelet ID token (ใช้ครั้งเดียว ไม่ persist) POST /api/line-session
4 Omelet LINE id_token + client_id (LINE channel ID) POST LINE verify
5 LINE Omelet sub (LINE user ID), aud, exp JSON จาก LINE
6 Omelet LIFF / Mini App cookie sony_line_session ที่เซ็น HMAC และ { ok: true } Set-Cookie HttpOnly
7 LIFF / Mini App Omelet LINE user ID ใน query lineuuid (หน้า Mini App ปัจจุบัน) GET /api/my-badges และ /api/my-products / /api/my-missions
8 Omelet Sony APIM { countryCode, lineId } + subscription key POST QueryWarrantyMySonyByLine
9 Sony APIM Omelet prodDetails[]: modelName, serialNumber, registrationDate JSON ตอน request ไม่ persist ที่ Omelet
10 Omelet ↔ D1 MySQL อ่านกฎเหรียญ; เขียน log ที่ hash LINE ID (เส้นทาง legacy shelf) TLS เมื่อ DATABASE_SSL=true
11 Omelet LIFF / Mini App สถานะเหรียญ, รูป, ความคืบหน้า; ซีเรียลเฉพาะหน้ารายละเอียดสินค้าที่ปลดล็อก JSON cache: no-store
12 LIFF / Mini App Sony websites ผู้ใช้กดลงทะเบียน / บัญชี / inquiry — แอปไม่แนบ LINE ID ใน query NEXT_PUBLIC_ACCOUNT_URL, register URL, sony.co.th microsite
เส้นทางเสริม: /entry ตรวจ Origin/Referer แล้วดู cookie ก่อนส่งไป /badges หน้า /share/... ให้ Facebook/OG อ่านแค่ชื่อและรูปเหรียญจากกฎ ไม่เรียก Sony API

ลำดับหลักเมื่อเปิด Mini App (Happy path)

1
LINE → Mini App ผู้ใช้เปิด LIFF endpoint ผู้ใช้เห็นหน้า my-badges ใน webview
2
Mini App → LINE → Omelet → LINE ไคลเอนต์ init LIFF, ส่ง ID token ไป Omelet, Omelet verify กับ LINE แล้วตั้ง cookie ไคลเอนต์เก็บ LINE user ID ใน sessionStorage
3
Mini App → Omelet → Sony → Omelet เรียก /api/my-* ด้วย lineuuid Omelet ขอสินค้าจาก warranty API แล้วอ่านกฎจาก MySQL
4
Omelet → Mini App คำนวณ Eligible Product / Threshold / Tier ในโปรเซส แล้วส่ง JSON แสดงผล ไม่บันทึก ownership ลงฐานข้อมูลของ Omelet
Cookie ใช้บังคับตัวตนบน /api/customer-products และ /entry หน้า Mini App ปัจจุบันส่ง LINE ID ผ่าน query ไป /api/my-*

PDPA Data Inventory / Retention

ประเภทข้อมูล วัตถุประสงค์ ระยะเวลาจัดเก็บ และแนวทางลบข้อมูล ตามที่ Sony Badge Pilot ทำจริงในโค้ด

เอกสารนี้เป็นคลังข้อมูลเทคนิค ไม่กำหนดนโยบายกฎหมายให้ Sony ระยะเวลาที่ระบุคืออายุที่ระบบตั้งไว้ หรือช่องว่างเมื่อโค้ดไม่ลบอัตโนมัติ ยังรอ Security / PDPA ยืนยันระยะเก็บที่ถูกต้องตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล
  • ขอบเขต
  • คลังข้อมูล
  • ระยะเวลาจัดเก็บ
  • แนวทางลบ

ขอบเขต (Scope)

ผู้ควบคุมแหล่งสินค้า รายการสินค้าที่ลงทะเบียน (รุ่น, ซีเรียล, วันลงทะเบียน) อยู่ที่ Sony warranty API Mini App ดึงมาคำนวณตอน request แล้วทิ้ง ไม่เก็บสำเนาใน MySQL ของแอป
สิ่งที่แอปถือครอง ตัวตนชั่วคราว (cookie / sessionStorage), ผลคำนวณที่ส่งกลับเบราว์เซอร์, และ log ที่ hash LINE ID บนเส้นทาง legacy shelf
ไม่ใช่ข้อมูลส่วนบุคคลของลูกค้า กฎเหรียญ, รายการ SKU ในเงื่อนไข, รูปเหรียญ, URL สินค้า, ข้อความ support

ไม่มี API สำหรับสิทธิเข้าถึง / ลบข้อมูลตามคำขอเจ้าของข้อมูล (DSAR) ในแอปนี้ การลบข้อมูลลูกค้าในระบบสินค้าต้องทำที่ Sony ไม่ใช่ที่ตารางกฎเหรียญ

คลังข้อมูล (Data inventory)

ข้อมูลส่วนบุคคลและข้อมูลที่เกี่ยวข้องกับบุคคล
ประเภทข้อมูล ตัวอย่างฟิลด์ แหล่งที่มา วัตถุประสงค์ ผู้ที่เห็นในแอป
ตัวระบุ LINE LINE user ID (sub / lineuuid) LIFF ID token และ liff.getProfile() ระบุผู้ใช้เพื่อเรียก warranty และแสดงเหรียญของผู้นั้น เซิร์ฟเวอร์; ไคลเอนต์เก็บใน sessionStorage และ query
โทเคนยืนยันตัวตน LINE ID token LIFF getIDToken() ยืนยันกับ LINE ครั้งเดียวตอนสร้าง session ส่งไป LINE แล้วไม่ persist
โปรไฟล์ LINE display name, picture URL LIFF profile บนอุปกรณ์ผู้ใช้ แสดงชื่อและรูปบนหน้า my-badges เบราว์เซอร์ของผู้ใช้; ไม่เขียนลง MySQL
ความเป็นเจ้าของสินค้า modelName/SKU, serialNumber, registrationDate Sony APIM prodDetails คำนวณ Eligible Product / Threshold / Tier และแสดงซีเรียลบนหน้ารายละเอียดที่ปลดล็อก เซิร์ฟเวอร์ตอน request; ไคลเอนต์เฉพาะสินค้าที่ปลดล็อก
ผลเหรียญที่คำนวณ สถานะ earned/locked, จำนวนที่ match, รูปเหรียญ คำนวณในแอปจากสินค้า + กฎ แสดงชั้นเหรียญและความคืบหน้า ผู้ใช้บน Mini App; หน้าแชร์มีแค่ชื่อ/รูปกฎ
บันทึกการคำนวณ (legacy) customer_line_uuid_hash, จำนวน SKU, earned_badges_json (รหัสเหรียญ ไม่มีซีเรียล) เส้นทาง /api/customer-products ตรวจสอบการทำงาน ไม่ใช่คลังลูกค้า ผู้มีสิทธิ์เข้า MySQL
ข้อมูลที่รับแล้วไม่ใช้ warrantyExpiryDate Sony APIM — ตัวแปลงปัจจุบันทิ้งค่านี้ ไม่แสดง ไม่เก็บ

ระยะเวลาจัดเก็บ (Retention)

อายุที่ระบบกำหนด vs สิ่งที่ยังไม่มีนโยบายในโค้ด
ที่เก็บ ข้อมูล ระยะเวลาในโค้ด หมดอายุอัตโนมัติหรือไม่
หน่วยความจำ request (เซิร์ฟเวอร์) warranty JSON, LINE ID ตอนคำนวณ จบ request ใช่ — ไม่เขียนตารางสินค้า
Cookie sony_line_session LINE ID + expiresAt (base64 + HMAC) 1 ชั่วโมง (Max-Age=3600) ใช่ — เบราว์เซอร์ทิ้งคุกกี้; เซิร์ฟเวอร์ปฏิเสธเมื่อหมดอายุ
sessionStorage คีย์ sony_line_uuid LINE user ID ดิบ จนปิดแท็บ ใช่ ตามพฤติกรรมเบราว์เซอร์ ไม่มีปุ่มลบในแอป
localStorage sonyBadgeCache:v1 ผลเหรียญเส้นทาง legacy + cache key ที่เป็น hash จนกว่าจะไม่ตรง badge_rules_version หรือโค้ดลบคีย์ บางส่วน — invalidate เมื่อกฎเปลี่ยน; ไม่มี TTL ปฏิทิน
MySQL badge_calculation_logs HMAC ของ LINE ID และสรุปเหรียญ ไม่กำหนด ไม่ — ไม่มี job ลบหรือ archive
Cache กฎในโปรเซส กฎเหรียญ ไม่ใช่ข้อมูลลูกค้า 60 วินาที ใช่
Sony warranty (นอกแอป) สินค้าที่ลูกค้าลงทะเบียน อยู่ที่นโยบาย Sony แอปนี้ไม่ควบคุม
App Service / stdout logs อาจมี LINE ID ดิบจาก console.log บางจุด ตามการตั้งค่า Azure / แพลตฟอร์ม แอปไม่ลบ log โครงสร้างพื้นฐาน
หน้า Mini App ปัจจุบัน (/api/my-*) ใช้ cache: "no-store" จึงไม่เก็บผลเหรียญลง localStorage

แนวทางลบข้อมูล (Deletion)

สิ่งที่ทำได้อัตโนมัติ vs ที่ต้องทำด้วยปฏิบัติการ
ข้อมูล แนวทางลบที่มีในระบบ แนวทางปฏิบัติการที่ยังต้องกำหนด
LINE ID token ไม่เก็บหลัง verify — ไม่มีสำเนาให้ลบ —
Cookie session หมดอายุใน 1 ชั่วโมง; ผู้ใช้ล้างคุกกี้ของโดเมนได้ ไม่มี endpoint เพิกถอน session ทั้งเครื่อง
sessionStorage LINE ID หายเมื่อปิดแท็บ; มีฟังก์ชัน clearStoredLineUuid ในโค้ดแต่ไม่ได้ผูกปุ่มลบบัญชี ถ้าต้องการลบตอน logout ให้เรียกเคลียร์ storage และไม่ใส่ lineuuid ใน URL
ผลเหรียญในเบราว์เซอร์ (legacy cache) โค้ดลบคีย์เมื่อ cache ไม่ตรงหรือโหลดไม่สำเร็จ ผู้ใช้ล้างข้อมูลเว็บไซต์ได้เอง
สินค้า / ซีเรียลใน MySQL ของแอป ไม่มีแถวให้ลบ — แอปไม่ persist แก้หรือลบที่ระบบลงทะเบียนสินค้าของ Sony
badge_calculation_logs ไม่มีงานลบอัตโนมัติ ผู้ดูแล DB ลบตามช่วงเวลา เช่น DELETE FROM badge_calculation_logs WHERE created_at < ... หรือลบแถวที่ hash ตรงกับเจ้าของข้อมูล (ต้องมี LOG_HASH_SECRET ชุดเดียวกับตอนเขียน)
กฎเหรียญ ไม่ลบตามคำขอลูกค้า — ไม่ใช่ข้อมูลบุคคล ปิดด้วย is_active = false ผ่าน seed ที่รีวิว
สำเนาใน log โครงสร้างพื้นฐาน แอปไม่จัดการ นโยบาย retention ของ Azure App Service / SIEM ของ Sony

เมื่อมีคำขอลบจากเจ้าของข้อมูล

  1. ยืนยันตัวตนกับกระบวนการ PDPA ของ Sony ไม่ใช้ Mini App เป็นช่องรับคำขอ
  2. ลบหรือแก้ความเป็นเจ้าของสินค้าที่ warranty / ระบบลงทะเบียนของ Sony (แหล่งข้อมูลหลัก)
  3. ถ้ายังเก็บ log การคำนวณ: คำนวณ HMAC ของ LINE ID ด้วย secret ปัจจุบัน แล้วลบแถวใน badge_calculation_logs
  4. แจ้งว่า cookie และ sessionStorage อยู่บนเครื่องผู้ใช้ — แนะนำให้ล้างข้อมูลเว็บของโดเมน Mini App
  5. ตรวจ log แพลตฟอร์มหากช่วงนั้นมี console.log ของ LINE ID ดิบ
Pilot ยังไม่มี retention job, ไม่มีหน้าลบบัญชี และไม่ลบ hash log อัตโนมัติ ต้องกำหนดระยะเก็บ (เช่น 90 วัน) นอกโค้ดแล้วให้ผู้ดูแล DB ทำให้สอดคล้องก่อนขึ้น production กว้าง
