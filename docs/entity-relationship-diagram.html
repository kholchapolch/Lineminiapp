ขอบเขต (Scope)

ERD นี้ครอบคลุมตารางที่เก็บ การตั้งค่าเหรียญ (badge configuration) เท่านั้น ไม่รวมข้อมูลลูกค้าที่มาจาก Sony API หรือเซสชัน LINE

อยู่ในแผนภาพ (In diagram) app_config, badge_display_groups, badge_rules, badge_rule_thresholds, badge_rule_conditions
อยู่นอกโมเดลนี้ (Out of this model) Sony products จาก warranty API, LINE session cookie / sessionStorage, และผลลัพธ์ที่ cache ในเบราว์เซอร์ localStorage ไม่ได้เก็บเป็นตารางในฐานข้อมูลนี้
badge_calculation_logs มีใน schema แต่ไม่มี foreign key ไปยังกฎ และไม่ใช่ data model ของการตั้งค่าเหรียญ — ดูส่วนท้ายของเอกสาร (present in schema, but it is an operational log, not a rule entity).

แผนภาพความสัมพันธ์ (Entity Relationship Diagram)

กล่องแสดง entity ตามตารางจริง คีย์หลักขีดเส้นใต้ เส้นทึบคือ foreign key จริง เส้นประคือความสัมพันธ์เชิงตรรกะที่ไม่มี CONSTRAINT

เส้นทึบ = physical FK (ON DELETE CASCADE) เส้นประ = logical only ไม่มี FOREIGN KEY || = หนึ่ง (one)   o< = ศูนย์หรือหลาย (zero or many)

จุดออกแบบที่ต้องรู้ (Design notes)

sony_skus เป็น JSON ไม่มีตาราง SKU แยก SQL จึง enforce รายการ SKU เป็นแถวไม่ได้ ยอมรับใน pilot เพราะ SKU เป็นตัวระบุภายนอกจาก Sony (ADR 0001)
หน้าต่างวันที่สองแบบ active_from / active_to ควบคุมการแสดงผลบนชั้นเหรียญ registration_start / registration_end ควบคุมหน้าต่างลงทะเบียนที่นับความคืบหน้า
เวอร์ชันกฎ เมื่อเปลี่ยนกฎ ระดับ หรือเงื่อนไข ต้อง bump app_config.badge_rules_version เพื่อให้ cache ของเบราว์เซอร์และ cache ในโปรเซสไม่ใช้ของเก่า
Composed rule กฎหนึ่งอันมีได้หลาย condition และหลาย threshold เช่น Trinity Master ใช้หลายแถว any เพื่อบังคับครบทุกตระกูลเลนส์ โมเดลนี้ไม่ใช่ boolean expression แบบซ้อนชั้น
การคำนวณเหรียญทำใน application code เพราะสินค้าที่ลูกค้ามีมาเป็น JSON จาก Sony API ตอน request ไม่ได้เก็บ ownership เป็นตารางใน MySQL นี้

ตารางปฏิบัติการที่ไม่อยู่ใน ERD หลัก (Operational table)
