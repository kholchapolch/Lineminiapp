Digital Badge Release Coordination

การประสานงานปล่อย Digital Badge (LINE Mini App) ลำดับงาน ฝ่ายที่เกี่ยวข้อง และเกณฑ์ Go / No-Go

อิงจากสิ่งที่มีในรีโป: แอป Next.js, seed/migrate MySQL, workflow UAT ไป App Service mysonybadgestg Production ยังไม่มี pipeline ใน Git — ประสานตามหลักเดียวกับ UAT เมื่อมีโฮสต์

ขอบเขตที่ต้องประสานพร้อมกัน

สายงาน สิ่งที่ต้องพร้อม หมายเหตุจากรีโป
แอป Mini App โค้ดที่ build ผ่าน, package Windows (server.js, web.config) Deploy อัตโนมัติเมื่อ push สาขาตาม workflow (ปัจจุบัน dev)
Configuration / Secret UAT_ENV_FILE (หรือ env โปรดักชันเมื่อมี), publish profile, LIFF / APIM / DB NEXT_PUBLIC_* ต้องมีตอน build — แก้ทีหลังอย่างเดียวไม่พอ
ฐานข้อมูลกฎเหรียญ migrate + seed + verify, ค่า badge_rules_version ไม่ได้อยู่ใน GitHub Actions — รันจากโฮสต์ที่เข้า MySQL ได้
สินทรัพย์รูปเหรียญ ไฟล์ใน /product-badge/, /quest-badge/ หรือ URL blob ตามชุด seed ชุด default กับชุด prod คนละรูปแบบ path
LINE LIFF Endpoint URL, Channel / LIFF ID ตรง env ต้อง HTTPS ของโดเมนแอป
Sony warranty APIM โหมด live หรือ mock, subscription key เมื่อ live คีย์ไม่ commit
Azure App Service / เครือข่าย HTTPS, Access Restrictions, health path IP นอก allowlist ได้ 403 — ไม่ใช่แอปพัง
ธุรกิจ / UAT บน LINE บัญชีทดสอบ, เคสปลดล็อกเหรียญ, แชร์, ลงทะเบียนสินค้า ไม่มี e2e ใน CI
รายชื่อบุคคลและช่องทางติดต่อไม่อยู่ใน Git กรอกผู้ประสานหลักในวิกิภายในตอนส่งมอบ

ลำดับที่แนะนำ (ไม่สลับแอปกับกฎโดยไม่ตั้งใจ)

1. ล็อกขอบเขตรีลีส + Release Note
2. สำรองตารางกฎ (ถ้าจะ seed)
3. ยืนยัน env / LIFF / APIM / โดเมน (config:check ผ่านตอน build)
4. Deploy แอป (Actions) — จด Git SHA
5. Migrate / seed / verify ฐาน (ถ้ากฎเปลี่ยน) — จด badge_rules_version
6. อัปเดต LIFF endpoint ถ้าโดเมนหรือ path เปลี่ยน
7. Verify จาก IP ที่อนุญาต + เปิดใน LINE
8. บันทึก Deployment Record + ตัดสิน Go / No-Go
9. ถ้า No-Go: rollback แอป และ/หรือ restore กฎ ตามแผนสำรอง

ถ้าเปลี่ยนแค่ UI โดยไม่เปลี่ยนกฎ ข้ามขั้น seed ได้ ถ้าเปลี่ยนแค่กฎโดยไม่เปลี่ยนแอป ยังต้อง bump badge_rules_version เพื่อให้แคชฝั่งไคลเอนต์หมดอายุ

Checklist ก่อนปล่อย (Go / No-Go)

ติ๊กนอก Git หลังทำจริง — อย่าใส่ secret ในช่องหมายเหตุ
ข้อ ผ่านเมื่อ Go?
CI build config:check, db:seed:sql:check, test, lint, build ผ่าน ☐
Deploy แอป webapps-deploy สำเร็จ และมี SHA ใน Actions ☐
Smoke HTTP /api/health มี runtime":"nodejs" และ /deployment-check.html มีข้อความ smoke (หรือรู้แล้วว่า 403 เป็น Access Restriction) ☐
กฎในฐาน db:verify / db:verify:prod ตามชุดที่ตั้งใจ และเวอร์ชันตรงที่บันทึก ☐
LIFF ใน LINE เปิด Mini App ได้, สร้างเซสชัน, หน้าโฮมของ user โหลดเหรียญ ☐
Sony ข้อมูลสินค้า โหมดที่ตกลง (mock/live) ให้ผลตรงบัญชีทดสอบ ☐
รูป / แชร์ รูปเหรียญขึ้น, ปุ่มแชร์กดได้บนอุปกรณ์เป้าหมาย ☐
เอกสารรีลีส Release Note + Deployment Record กรอก SHA / วันที่ / ผู้ดำเนินการ ☐
No-Go ถ้า CI ไม่ผ่าน, health ไม่ขึ้นจากเครือข่ายที่อนุญาต, กฎในฐานไม่ตรงชุดที่ตั้งใจ, หรือเปิดใน LINE ไม่ได้สร้างเซสชัน

จุดที่มักหลุดตอนประสาน

  • Deploy แอปแล้วแต่ยังไม่ seed — ผู้ใช้เห็นกฎเก่าหรือตารางไม่ครบ
  • Seed ชุด default ทับฐานที่ต้องมีเหรียญ SEL1224GM (ชุด prod)
  • แก้เฉพาะ App Service setting แต่ไม่ rebuild — ค่า NEXT_PUBLIC_* ในคลายเอนต์ไม่เปลี่ยน
  • เปลี่ยนโดเมนแล้วไม่อัปเดต LIFF endpoint / APP_BASE_URL / ALLOWED_ORIGINS
  • ทดสอบจาก IP นอก allowlist แล้วสรุปว่าแอปพัง
  • สมมติว่า push ไป main จะขึ้น UAT ทั้งที่ YAML ทริกเกอร์ที่ dev

สิ่งที่ต้องบันทึกหลังปล่อย

  • สภาพแวดล้อม (UAT / Production)
  • วันที่–เวลา, ผู้ประสานหลัก, Git SHA
  • รัน DB หรือไม่ — ค่า badge_rules_version
  • โหมด Sony (mock / live) โดยไม่ใส่คีย์
  • ผล smoke และผลทดสอบใน LINE สั้นๆ
  • ถ้า rollback: SHA / dump ที่ใช้ย้อน

ใช้แม่แบบใน Deployment Record และเนื้อหาใน Release Note เป็นต้นทาง อย่า commit secret หรือ LINE ID ดิบในบันทึกสาธารณะ
