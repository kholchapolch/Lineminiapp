Developer and client review note

Mock Data, Debug Mode, And Live Usage

This document explains which data is mock-only, how to use each mock lineuuid, how debug mode behaves, and how production should use LINE session data instead of URL parameters.

Short Answer

In production, the badge page must not trust ?lineuuid=... from the URL. The server should resolve the LINE user from a verified LINE login/session cookie.

Mock lineuuid query strings are for local/demo testing only.

Mock Mode

SONY_PRODUCT_API_MODE=mock

Uses the mock customers and mock Sony product JSON inside the app.

Live Mode

SONY_PRODUCT_API_MODE=live

Calls Sony APIM server-side using the verified LINE user ID.

Debug Mode

Debug mode is controlled by the URL query ?debug=1.

Behavior Without debug With ?debug=1
Sony data source Depends on SONY_PRODUCT_API_MODE Same; debug does not switch mock/live mode
Browser cache Can reuse local badge result cache when metadata matches Bypasses browser badge result cache
Debug panel Hidden Visible in local/staging only
Production Normal production UI Debug trace is ignored/omitted

Local Demo URLs

  • /badge?lineuuid=demo-line-earned normal mock UI
  • /badge?lineuuid=demo-line-earned&debug=1 mock UI with debug panel
  • /api/customer-products?lineuuid=demo-line-earned&debug=1 API payload with debug trace in local/staging

If lineuuid is omitted in local mode, the app uses SONY_DEMO_LINE_UUID, defaulting to demo-line-earned.

Live Production Usage

In live mode, the server creates the Sony API request like this:

  • Mode: SONY_PRODUCT_API_MODE=live
  • Endpoint: SONY_PRODUCT_API_BASE_URL
  • Secret header: Ocp-Apim-Subscription-Key from SONY_PRODUCT_API_SUBSCRIPTION_KEY
  • Body: {"countryCode":"th","lineId":"<verified LINE user ID>"}

Production should resolve lineId from the signed LINE session created by the /entry flow or by /badge automatic LIFF recovery, not from ?lineuuid=....

URL parameters can be edited by users. Accepting production LINE IDs from URL params would let one user request another user's badge data.

Production Flow

  1. User opens the LIFF/LINE Mini App entry URL from an approved Sony source.
  2. The /entry route validates Origin/Referer against the configured allowlist.
  3. LIFF obtains a LINE ID token from the LINE client and sends it to /api/line-session.
  4. The server verifies the LINE ID token with LINE and stores the LINE user ID in a signed, HTTP-only session cookie.
  5. The badge page calls /api/customer-products without trusting a URL lineuuid.
  6. The server calls Sony APIM with the verified LINE user ID and calculates badges from DB rules.

If a user lands directly on /badge and the session is missing, the page attempts the same LIFF ID-token session creation automatically, then retries badge loading once.
