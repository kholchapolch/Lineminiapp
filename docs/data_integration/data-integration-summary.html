Integration Specification

ขอบเขตการเชื่อมต่อ ระบบต้นทาง–ปลายทาง วิธีรับส่งข้อมูล และความถี่ในการเชื่อมต่อ ของ Sony Badge Pilot ตามที่โค้ดเรียกจริง

  • ขอบเขต
  • ต้นทาง–ปลายทาง
  • สัญญาข้อมูล
  • ความถี่

ขอบเขตการเชื่อมต่อ (Scope)

ระบบนี้เป็น synchronous request/response ไม่มี message queue, webhook เข้า, หรือ batch job การเชื่อมต่อรันไทม์มีสี่เส้นทางหลัก

อยู่ในขอบเขต LINE LIFF (ไคลเอนต์), LINE ID token verify (เซิร์ฟเวอร์), Sony warranty APIM, MySQL กฎเหรียญ
นอกขอบเขต API ผู้ใช้กดไปเว็บ Sony (บัญชี / ลงทะเบียน / microsite) เป็นการนำทางเบราว์เซอร์ แอปไม่ส่ง LINE ID ติด query
ไม่เชื่อมต่อ ไม่มี CMS, ไม่เรียก Facebook Graph จากเซิร์ฟเวอร์, ไม่มี webhook จาก Sony เมื่อลูกค้าลงทะเบียนสินค้าใหม่
โหมด SONY_PRODUCT_API_MODE=mock ไม่เรียก APIM ใช้ข้อมูลจำลองในโปรเซส ใช้ได้ตามที่ตั้งค่า (local / หรือ UAT ที่ยังเป็น mock)

วิธีรับส่งข้อมูล (Contracts)

INT-01 LINE LIFF

ไลบรารี @line/liff ใช้ NEXT_PUBLIC_LIFF_ID เรียก liff.init, liff.getIDToken(), liff.getProfile() ต้องอยู่ภายใน LINE client

INT-03 LINE verify

ค่าเริ่มต้น URL: https://api.line.me/oauth2/v2.1/verify (ปรับได้ด้วย LINE_VERIFY_ID_TOKEN_URL) 

POST
Content-Type: application/x-www-form-urlencoded

id_token=<LIFF ID token>
client_id=<LINE_CHANNEL_ID>

แอปใช้ sub เป็น LINE user ID และตรวจ aud ให้ตรงช่อง ไม่ persist ID token

INT-02 Mini App ↔ Omelet

API Method ข้อมูลเข้า ข้อมูลออก
/api/line-session POST JSON { "idToken": "..." } { "ok": true } + cookie sony_line_session
/api/my-badges เป็นต้น GET query lineuuid, บางเส้นมี locale JSON เหรียญ/สินค้า/ภารกิจ; ไม่มีตัวตนถ้าไม่ส่ง lineuuid (ชั้นล็อก)
/api/customer-products GET cookie session (เส้นทาง diagnostic) shelf แบบตัด PII; อาจมี cache hint

URL มาจาก SONY_PRODUCT_API_BASE_URL ตัวอย่างสภาพแวดล้อมพัฒนา: https://apim-rcap-dev.azure-api.net/mysony-api/QueryWarrantyMySonyByLine 

POST

Ocp-Apim-Subscription-Key: <server-only secret>

{

  "lineId": "<LINE user ID>"

INT-05 MySQL

เชื่อมด้วย DATABASE_URL (โปรโตคอล mysql:) UAT ต้องเปิด TLS อ่าน badge_rules และตารางลูก ไม่ได้เก็บ ownership ของลูกค้า

INT-06 เว็บ Sony

NEXT_PUBLIC_ACCOUNT_URL, NEXT_PUBLIC_REGISTER_PRODUCT_URL, และลิงก์ inquiry ไป https://www.sony.co.th/microsite/digital-badge/ ไม่มี request body จากเซิร์ฟเวอร์แอป

ความถี่ในการเชื่อมต่อ (Frequency)

ไม่มี scheduler — เกิดตามการกระทำของผู้ใช้
Integration ทริกเกอร์ ความถี่โดยประมาณ Cache / จำกัดซ้ำ
INT-01 LIFF โหลด Mini App / LineSessionProvider ครั้งต่อแท็บจนกว่า session ในหน้าพร้อม init LIFF ใช้ promise รวมในโมดูล; โปรไฟล์เก็บใน sessionStorage ของแท็บ
INT-03 LINE verify POST /api/line-session ครั้งเมื่อสร้างหรือต่ออายุ session จาก LIFF cookie อายุ 1 ชั่วโมง ไม่ได้ refresh อัตโนมัติเป็นพื้นหลัง
INT-04 Sony APIM ทุกครั้งที่ /api/my-* มี lineuuid (และเส้นทาง customer-products แบบ cache miss) ต่อหน้า / ต่อการ fetch ของไคลเอนต์ ไม่มี polling ไคลเอนต์ my-* ใช้ cache: "no-store" จึงเรียก Sony ใหม่ทุกโหลด
INT-05 MySQL อ่านกฎ คู่กับคำนวณเหรียญ ต่อ request ที่ต้องใช้กฎ cache ในโปรเซส 60 วินาที ตาม badge_rules_version
INT-05 เขียน log เส้นทาง getBadgeResultForLineUuid (legacy shelf) ต่อครั้งที่คำนวณเส้นนั้น หน้า Mini App หลักไม่เขียนตารางนี้
INT-06 เว็บ Sony ผู้ใช้กดปุ่ม ตามการใช้งาน ไม่ใช่ตามรอบเวลา —
ไม่มี inbound webhook เมื่อลูกค้าเพิ่งลงทะเบียนสินค้าที่ Sony เหรียญจะอัปเดตเมื่อผู้ใช้เปิด Mini App แล้วแอปเรียก warranty API รอบใหม่

ข้อตกลงร่วม

  • Base path คือ origin ของแอป เช่น https://stglineminiapp.sony.co.th
  • JSON ใช้ Content-Type: application/json
  • ไม่มี version prefix เช่น /v1
  • ไม่มี CORS header พิเศษ — คาดว่าเรียก same-origin จาก Mini App
  • ไคลเอนต์ Mini App ส่ง cache: "no-store" เมื่อเรียก /api/my-*

Authentication

แบบ ตำแหน่ง รายละเอียด
LINE ID token JSON body idToken เซิร์ฟเวอร์ verify กับ LINE แล้วตั้ง cookie ไม่คืน LINE ID ใน JSON
Cookie sony_line_session Header Cookie HttpOnly, SameSite=Lax, อายุ 1 ชม. ใช้กับ /entry และ /api/customer-products
Query lineuuid URL query ใช้กับ /api/my-* ในปัจจุบัน ไม่ตรวจ cookie
Mini App ส่ง LINE user ID ใน query ของ XHR นี่คือสัญญาที่ใช้จริง ไม่ใช่โมเดลที่แนะนำด้านความปลอดภัย

Error code

เมื่อล้มเหลว บอดี้เป็น JSON:

{
  "code": "UNAUTHORIZED",
  "message": "LINE session is required."
}
HTTP code message (ที่ส่งให้ไคลเอนต์) เมื่อไหร่
400 MISSING_ID_TOKEN LINE ID token is required. body ไม่มี idToken ที่เป็นสตริงไม่ว่าง
400 MISSING_SKU At least one SKU is required. mock-session ไม่มี query sku
401 UNAUTHORIZED LINE session is required. (หรือข้อความ verify ไม่ผ่าน) ไม่มี/คุกกี้ไม่ถูกต้อง, token หมดอายุ, aud ไม่ตรง
404 NOT_FOUND Not found. / Product badge not found. / Mission badge not found. mock-session นอก local; สินค้า/ภารกิจไม่มีหรือยังไม่ปลดล็อก
404 CUSTOMER_NOT_FOUND Customer profile was not found. Sony APIM คืน 404 — ใช้บน /api/customer-products
500 SONY_PRODUCT_API_ERROR Badge data is temporarily unavailable. warranty API ไม่สำเร็จหรือรูปแบบไม่ถูก
500 UNKNOWN_ERROR Something went wrong. Please try again later. ข้อผิดพลาดที่ไม่มี safeMessage

/api/my-products และ /api/my-missions เมื่อ error มักคืนชั้นล็อก 200 แทน error JSON /api/my-badges คืน error JSON ตามตาราง

Product Name ไม่มีฟิลด์ชื่อทางการตลาดใน warranty response ใช้ badge_rules.badge_name เป็นชื่อบน UI ใส่ตอน seed เช่น FE 24-70mm F2.8 GM II
Category ไม่มีหมวดจาก Sony API displayGroupCode ของกฎ เช่น prime-lens badge_rules.display_group_code ↔ badge_display_groups.group_code
Serial Number prodDetails[].serialNumber serialNumber ไม่เก็บในกฎ
วันลงทะเบียน prodDetails[].registrationDate registeredAt เทียบกับ registration_start / registration_end
วันหมดประกัน warrantyExpiryDate ไม่ map ไม่ใช้
Warranty ไม่มี SKU แยกจากชื่อรุ่น แอปจึงใช้ modelName เป็นรหัสเทียบ ค่าในกฎต้องเป็นรหัสรุ่นแกน เช่น SEL2470GM2 ไม่ใช่สตริงเต็มอย่าง SEL2470GM2/QSYX

ฟิลด์ เหรียญผลิตภัณฑ์ เหรียญ Quest / Mission
Product Model (sku) ใช้ — ต้อง match sony_skus ของกฎนั้น (มักมีรุ่นเดียว) ใช้ — นับรุ่นที่อยู่ใน Eligible Product ของแต่ละ condition
Product Name ไม่ใช้คำนวณ ใช้แสดงชื่อ ไม่ใช้คำนวณ
Category ไม่ใช้คำนวณ ใช้จัดกลุ่มบน UI quest อยู่กลุ่ม quest
Serial Number ใช้ปลดล็อก ถ้ามีอย่างน้อยหนึ่งซีเรียลที่รุ่นตรง quantity = จำนวนซีเรียล ไม่ได้ใช้ซีเรียลเป็นรหัสเทียบ ไม่นับซ้ำต่อซีเรียล — นับรุ่นไม่ซ้ำ (unique SKU) ต่อเงื่อนไข
วันลงทะเบียน ต้องอยู่ในหน้าต่างลงทะเบียนของกฎ ถ้ากฎกำหนดไว้ (seed ปัจจุบันเป็น null = ไม่จำกัด) เช่นเดียวกันก่อนนับ matched count

กฎการเทียบรุ่น

  • uppercase + trim
  • เท่ากับรหัสในกฎ หรือขึ้นต้นด้วยรหัสนั้นแล้วส่วนที่เหลือเป็น suffix แคตตาล็อก เช่น /QSYX, SYX, QSYX
  • SEL70200GM ไม่ถือว่า match SEL70200G
ตัวอย่าง warranty → กฎ modelName: "SEL2470GM2/QSYX" → sku ภายในเป็นสตริงนั้น → match กฎ product-sel2470gm2 ที่ sony_skus: ["SEL2470GM2"]
ซีเรียลสองตัวรุ่นเดียวกัน เหรียญผลิตภัณฑ์: ปลดล็อก, quantity = 2, รายการ registrations สองแถว Quest: นับ 1 รุ่นในเงื่อนไขนั้น

Error Handling & Retry Flow

วิธีจัดการเมื่อเชื่อมต่อไม่สำเร็จ การ Retry และการบันทึก Log ของ LINE, Sony APIM, MySQL และ Mini App API

สถานะปัจจุบัน: ไม่มีการ retry / backoff ในแอป แต่ละการเรียกภายนอกเป็นครั้งเดียว (single attempt) ความล้มเหลวถูก map เป็นรหัสปลอดภัย หรือแสดงแคตตาล็อกล็อก

  • นโยบาย (Policy)
  • Retry
  • ลำดับเมื่อล้มเหลว (Failure flow)
  • รหัสข้อผิดพลาด (Error codes)
  • พฤติกรรมต่อ API
  • การบันทึก Log
  • ช่องว่าง (Gaps)

นโยบาย (Policy)

ไม่เปิดเผยรายละเอียดภายใน JSON สาธารณะใช้ toSafeError ข้อความทั่วไป เช่น “temporarily unavailable” ไม่ส่ง stack, token, หรือ serial
ไม่ retry อัตโนมัติ ไม่มี loop, ไม่มี exponential backoff, ไม่มี queue ผู้ใช้ต้องโหลดหน้าใหม่ หรือเข้าหน้าอีกครั้ง
สองแบบการตอบผู้ใช้ /api/customer-products ส่ง HTTP error · /api/my-products และรายการภารกิจส่วนใหญ่ พยายามคืนหน้าล็อกแทน

การเชื่อมต่อที่อาจล้ม: LIFF init, LINE verify ID token, Sony QueryWarrantyMySonyByLine, MySQL กฎเหรียญ ไม่มี webhook / job ที่ retry ภายหลัง

Retry

สิ่งที่มีและไม่มี (What exists)
ชั้น (Layer) Retry ในโค้ด พฤติกรรมจริง (Actual behavior)
Sony APIM fetch ไม่มี ครั้งเดียว · ไม่มี AbortSignal · ไม่มี timeout ในแอป
LINE verify ID token ไม่มี HTTP ไม่สำเร็จ → UNAUTHORIZED ทันที
LIFF liff.init รีเซ็ต promise เมื่อล้ม ครั้งถัดไปที่เรียก getCurrentLiffClient จะ init ใหม่ ไม่ใช่ retry ภายในครั้งเดียว
ไคลเอนต์ Mini App ไม่มีปุ่ม retry อัตโนมัติ useLineSessionData fetch ครั้งเดียวต่อ lineUuid · ยกเลิกด้วย AbortController เมื่อ unmount
MySQL pool ไม่ใช่ retry ของธุรกิจ waitForConnections: true, connectionLimit: 10 คิวรอ connection ในพูล ไม่ลอง query ซ้ำเมื่อ query ล้ม
เขียน badge_calculation_logs ไม่ retry .catch(() => undefined) ทิ้งความล้มเหลวของการเขียน log เพื่อไม่ให้บังหน้าผลคำนวณ
คำว่า “Please try again later” ใน UNKNOWN_ERROR เป็นข้อความผู้ใช้ ไม่ได้หมายความว่าเซิร์ฟเวอร์จะลองใหม่ให้

ลำดับเมื่อเชื่อมต่อไม่สำเร็จ (Failure flow)

Sony warranty (INT-04)

getCustomerProducts(lineId)
  │
  ├─ ไม่มี subscription key → SONY_PRODUCT_API_ERROR
  ├─ HTTP 404              → CUSTOMER_NOT_FOUND
  ├─ HTTP อื่นที่ไม่ใช่ 2xx → SONY_PRODUCT_API_ERROR
  ├─ payload ไม่ครบ        → SONY_PRODUCT_API_ERROR
  └─ เครือข่ายค้าง/timeout ของแพลตฟอร์ม
                           → ไม่มีรหัส TIMEOUT (กลายเป็น UNKNOWN หรือ API error)

เส้นทางคำนวณเหรียญแบบมี log

เฉพาะ getBadgeResultForLineUuid (ใช้โดย GET /api/customer-products) 

try Sony + MySQL rules + calculate
  ├─ สำเร็จ → writeBadgeCalculationLog (hash, นับ SKU, สรุปเหรียญ)
  │           .catch เงียบถ้า DB เขียนไม่ได้
  └─ ล้ม    → writeBadgeCalculationLog (error_code, error_message ที่ปลอดภัย)
             แล้ว throw ต่อ → HTTP 401 / 404 / 500

เส้นทาง Mini App (my-*)

GET /api/my-products | /api/my-missions
  ├─ ไม่มี lineuuid     → แคตตาล็อกล็อก (ไม่เรียก Sony)
  ├─ Sony/DB ล้ม         → พยายามแคตตาล็อกล็อก HTTP 200
  └─ โหลดกฎล็อกไม่ได้   → 500 { code, message }

GET /api/my-badges
  └─ ล้ม → 500 ทันที (ไม่มี fallback ล็อกใน route นี้)
           และ console.log locale + lineuuid ดิบ

GET /api/my-products/[id] | /api/my-missions/[id]
  ├─ ไม่พบรหัสในกฎ      → 404 NOT_FOUND
  └─ Sony ล้ม (detail)   → mission มี fallback ล็อก; product detail ส่ง 500

LINE session

LIFF getIDToken → POST /api/line-session
  ├─ ไม่มี idToken        → 400 MISSING_ID_TOKEN
  ├─ LINE verify ไม่ผ่าน  → 401 UNAUTHORIZED
  └─ ข้อผิดพลาดอื่น       → 500 UNKNOWN_ERROR
ไคลเอนต์: response ไม่ ok → throw "LINE session could not be verified."
getLineProfile จาก LIFF ล้ม → คืน null (ไม่บล็อกเซสชัน)

รหัสข้อผิดพลาด (Error codes)

รหัสที่ไคลเอนต์อาจเห็น (Public codes)
code HTTP โดยทั่วไป สาเหตุ (Cause) ข้อความปลอดภัย (safeMessage)
MISSING_ID_TOKEN 400 body ไม่มี idToken LINE ID token is required.
UNAUTHORIZED 401 ไม่มีคุกกี้เซสชัน หรือ LINE verify ล้ม LINE session is required. (หรือข้อความ verify)
CUSTOMER_NOT_FOUND 404 Sony HTTP 404 หรือ mock ไม่รู้จัก lineuuid Customer profile was not found.
NOT_FOUND 404 productId / missionId ไม่อยู่ในกฎ หรือยังไม่ปลดล็อก Product / Mission badge not found.
SONY_PRODUCT_API_ERROR 500 APIM ไม่สำเร็จ หรือ payload ไม่ถูกต้อง Badge data is temporarily unavailable.
UNKNOWN_ERROR 500 error ที่ไม่มี code + safeMessage Something went wrong. Please try again later.

toSafeError คืนรหัสต้นทางเฉพาะเมื่อ object มีทั้ง code และ safeMessage เป็นสตริง Error ของ MySQL ดิบจะกลายเป็น UNKNOWN_ERROR

พฤติกรรมต่อพื้นผิว API (Per-surface behavior)

เมื่อ Sony หรือฐานข้อมูลล้มเหลว
Endpoint ผู้ใช้เห็น (User-facing) เขียน calculation log
GET /api/customer-products JSON error + HTTP 404/500 ใช่ (hash เท่านั้น)
GET /api/my-products, GET /api/my-missions แคตตาล็อกล็อก HTTP 200 ถ้าโหลดกฎได้ ไม่
GET /api/my-badges 500 JSON error · หน้าบ้านแสดงวิวว่าง ไม่
GET /api/health เสมอ { status: "ok" } ไม่ตรวจ Sony/DB

หน้า Mini App ไม่มีปุ่ม “ลองใหม่” แยก การโหลดใหม่ของ LIFF หรือเปลี่ยน lineUuid จะยิง fetch อีกครั้งหนึ่ง

การบันทึก Log (Logging)

1. Application console (stdout ของ App Service)

ตำแหน่ง สิ่งที่พิมพ์ ความเสี่ยง (Risk)
sony-products-client.ts getCustomerProducts + lineuuid ดิบ PII ใน log ของแพลตฟอร์มทุกครั้งที่เรียก Sony
GET /api/my-badges { locale, lineuuid } PII
GET /api/my-missions { lineuuid } และเมื่อล้ม { error } อาจมี stack / รายละเอียดภายใน
catch ของ my-badges { safeError } รหัสปลอดภัยเท่านั้น

2. ตาราง badge_calculation_logs

เขียนแบบ fire-and-forget จาก getBadgeResultForLineUuid ถ้าไม่มี DATABASE_URL จะข้าม

คอลัมน์ที่เก็บ (Stored columns)
คอลัมน์ เนื้อหา
customer_line_uuid_hash HMAC-SHA256 ของ lineuuid ด้วย LOG_HASH_SECRET หรือ fallback APP_SESSION_SECRET ไม่เก็บ LINE ID ดิบ
source_sku_count จำนวนสินค้าจาก Sony (เมื่อล้มเป็น 0)
matched_sku_count ผลรวม matchedCount ของเหรียญที่คำนวณ
earned_badges_json อาร์เรย์ { code, status, matchedCount } เมื่อล้มเป็น []
error_code / error_message จาก toSafeError เมื่อ catch สำเร็จเป็น NULL
created_at timestamp · มี index เรียงใหม่ก่อน
Mini App ที่ใช้ getBadgeExperienceForLineUuid ไม่เขียนแถวนี้ การเปิด my-badges / my-products จึงไม่เหลือประวัติ error ในตาราง แม้ Sony จะล้ม

ไม่มี job ลบ log ตามอายุ (retention) การลบต้องทำนอกแอป

3. สิ่งที่ไม่ถูก log

  • ไม่ส่ง log ไป SIEM / Application Insights จากโค้ดแอปโดยตรง
  • ไม่เก็บ serial, modelName, ID token ในตาราง log
  • /api/customer-products ตัด serial ออกจาก JSON แสดงผล แต่ debug trace แบบ local ยังมีชุดข้อมูลที่ redact แล้ว

ช่องว่าง (Gaps)

  • กำหนด timeout + retry นโยบายชัด (เช่น 1 ครั้งเมื่อ 502/503/timeout จาก APIM) และรหัส TIMEOUT แยกจาก SONY_PRODUCT_API_ERROR
  • หยุดพิมพ์ lineuuid ดิบใน console ให้ใช้ hashLineUuid
  • เขียน calculation log จากเส้นทาง my-* ด้วย หรือรวมให้เหลือแหล่งเดียว
  • ทำ health check ที่ตรวจ MySQL / APIM แยกจาก liveness ของโปรเซส
  • ปุ่มหรือข้อความ “ลองใหม่” บน Mini App เมื่อเป็น 500 จริง (ตอนนี้ my-products อาจดูเหมือน “ยังไม่มีเหรียญ” ทั้งที่ Sony ล่ม)
  • GET /api/my-missions มีโค้ดหลัง return ใน catch ที่ไม่ถูกเรียก fallback 500 เมื่อโหลดแคตตาล็อกล็อกไม่ได้จึงไม่ทำงานใน route นี้
