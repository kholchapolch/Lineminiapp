Data Model

badge_rules
parent rule

display metadata

levels / targets / images

match type / SKU JSON
badge_calculation_logs

จุดสำคัญ: badge_display_groups ไม่มี foreign key ไป badge_rules. Runtime grouping อ่าน badge_rules.display_group_code โดยตรง จึงต้องสะกด code ให้ตรงกันเอง
Schema dynamic แต่ UI บางส่วนใช้ fixed IDs: เพิ่ม Product Badge ใน group เดิม หรือแก้ rule เดิมทำด้วย DB ได้ แต่การเพิ่ม Product group ใหม่ ต้องแก้ PRODUCT_FILTER_IDS และ i18n. การเพิ่ม Quest section ใหม่ต้องแก้ MissionSectionId, ข้อความ TH/EN และ tests ก่อน activate rule

Table Reference

อธิบายแต่ละ table

Table หน้าที่ Column สำคัญ แก้เมื่อไร ข้อควรระวัง
app_config Key/value ของ runtime key, value ทุก rule change ต้องเปลี่ยน badge_rules_version Version ใช้เป็น cache key; ไม่ bump อาจเห็น rule เก่านานถึง cache TTL
badge_display_groups Catalog ของหมวดแสดงผล เช่น Prime Lens, Quest group_code, badge_type, sort_order, is_active เพิ่มหมวดใหม่ หรือเปลี่ยนชื่อ/ลำดับหมวด ไม่มี FK; ต้องให้ group_code ตรงกับ rule
badge_rules Parent row ของ Badge/Quest หนึ่ง rule badge_code, type, group, product model/url, dates, is_active เพิ่ม rule, เปลี่ยน metadata, date window หรือ deactivate badge_code ต้อง stable และ unique; อย่า update id
badge_rule_thresholds ระดับปลดล็อกและรูปที่แสดง level, required_count, image URLs, sort_order เพิ่ม Bronze/Silver/Gold, เปลี่ยน target หรือรูป Unique ต่อ (badge_rule_id, level); target สูงสุดต้องไม่เกิน condition cap
badge_rule_conditions เงื่อนไข SKU ที่ทำให้ progress เพิ่ม match_type, required_count, sony_skus JSON เพิ่ม/ลบ SKU, เปลี่ยน any/all/min_count, ทำหลาย family JSON ต้อง valid; SKU ซ้ำข้ามหลาย condition อาจถูกนับซ้ำใน matched count
badge_calculation_logs Log ผลคำนวณแบบ hash LINE UUID สำหรับ diagnosis source/matched counts, result JSON, error, timestamp ระบบเขียนอัตโนมัติ ใช้อ่านตรวจปัญหา ไม่ใช่ config table; ไม่ insert/update เพื่อสร้าง badge
Column behavior ที่มักสับสน
  • badge_type: product หรือ quest.
  • rule_type: tier หรือ achievement.
  • active_from/to: คุมว่าตัว rule active ตอนนี้หรือไม่.
  • registration_start/end: คัดเฉพาะสินค้าที่ registered อยู่ในช่วง.
  • locked_image_url = NULL: runtime fallback ไปใช้ achieved image.
  • share_image_url = NULL: หน้า share อาจ fallback ไป image หลัก.
  • การลบ row ใน badge_rules จะ cascade ลบ thresholds/conditions.
  • Product group ใหม่ต้อง sync src/lib/my-products/types.ts และ i18n; Quest code ใหม่ต้อง sync src/lib/my-missions/types.ts และ i18n.

Rule Semantics

Logic ที่ต้องรู้ก่อนเขียน SQL

any

มีอย่างน้อย N จากกลุ่ม

ปกติใช้ required_count = 1 สำหรับ “มีสักหนึ่งรุ่นใน family”.

count = MIN(unique matched SKU, required_count)
min_count

สะสมอย่างน้อย N รุ่น

เหมาะกับ tier เพราะขยาย target เป็น 2/3/5 ได้ และนับ model/SKU ไม่ซ้ำ.

count = MIN(unique matched SKU, required_count)
all

ต้องครบทุก SKU

Runtime ใช้จำนวนสมาชิกใน sony_skus เป็น cap แม้ค่า required_count จะต่าง.

count = MIN(unique matched SKU, sony_skus.length)
หลาย conditions: matched count ของแต่ละ condition ถูกบวกเข้าด้วยกัน. ใช้สร้าง Trinity แบบ “any 1 จาก family A + any 1 จาก B + any 1 จาก C” ได้ แต่ควรใช้ SKU sets ที่ไม่ overlap; SKU เดียวอยู่หลาย condition อาจเพิ่ม count หลายครั้ง
RequirementConditionsThresholds
Product badge ต่อหนึ่งรุ่น any / 1 / [MODEL_CODE] achievement = 1
สะสม 2/3/5 รุ่นจาก list เดียว min_count / 5 / [SKU list] Bronze 2, Silver 3, Gold 5
มีหนึ่งรุ่นจากแต่ละ 3 family สาม rows แบบ any / 1 achievement = 3
ต้องมีครบทุก SKU all / จำนวน SKU / [SKU list] Target เท่าจำนวน SKU
Date window: registration_end เทียบด้วยวันที่และรวมวันสิ้นสุด. ส่วน active_to ถูกอ่านเป็นเวลา 00:00 UTC; ถ้าต้องการให้ active ครบทั้งวัน ให้ทดสอบ boundary และพิจารณาตั้งเป็นวันถัดไป

Safe Delivery

ขั้นตอน UAT → PROD

Deploy app ไม่ได้ update database. Workflow ปกติ build/deploy application เท่านั้น. ต้องรัน SQL ที่ review แล้วกับ UAT/PROD database แยกต่างหาก
  1. Review requirement: ระบุ badge code, display group, SKU list, match type, target, รูป, product URL, campaign dates และ rollback owner.
  2. ตรวจ image ก่อน: URL ต้องตอบ 200, content type เป็น image และ PROD ต้องใช้ https://mysonybadgestorageprd.blob.core.windows.net/....
  3. Sync source: UAT ใช้ scripts/db/seed-data.mjs, PROD ใช้ scripts/db/prod/seed-data.mjs. Environment image URLs อาจต่างกัน.
  4. Backup: dump 5 config tables ก่อนเปลี่ยน UAT/PROD.
  5. Execute targeted SQL ใน transaction และตรวจ affected rows.
  6. Bump badge_rules_version ใน transaction เดียวกัน.
  7. Verify DB + API + LINE flow; รอ cache refresh สูงสุดประมาณ 60 วินาที.
  8. เก็บ evidence: ticket, SQL version, before/after counts, test account, URLs.
Code validation หลัง sync seed source 
# PROD source
# scripts/db/prod/seed-data.mjs

# Generate SQL สำหรับ review เท่านั้น; อย่ารันทั้งไฟล์จนกว่าจะ review full dataset
npm run db:seed:sql:prod

npm test
npm run lint
npm run build

# ตรวจ diff/status แล้วเปิด generated SQL review ทั้งไฟล์
git diff -- scripts/db/prod/seed-data.mjs
git status --short scripts/db/prod/seed-all-rules.sql

Backup command

# รันจาก network ที่เข้าถึง Azure MySQL private endpoint ได้
# อย่าใส่ password ลงใน command history
mysqldump \
  --host=<DB_HOST> \
  --port=3306 \
  --user=<DB_USER> \
  --password \
  --ssl-mode=REQUIRED \
  --single-transaction \

อย่าใช้ full seed เพื่อแก้ rule เดียวโดยไม่ review ทั้ง dataset. scripts/db/seed.mjs replace groups/thresholds/conditions และลบ obsolete rules ที่ไม่อยู่ใน source. Targeted SQL ลด blast radius กว่า

SQL Example 1

เพิ่ม Product Badge รุ่นใหม่

ตัวอย่างนี้เพิ่มหนึ่ง Product Badge เข้า group เดิม พร้อม threshold และ condition อย่างละหนึ่ง row. แก้ค่าที่ขึ้นต้น REPLACE_ME_ ทุกจุดก่อนใช้ 

-- CASE: เพิ่ม Product Badge รุ่นใหม่
-- Run UAT ก่อน แล้วใช้ค่ารูป/URL ของ environment ให้ถูกต้อง
SET NAMES utf8mb4;
START TRANSACTION;

SET @model_code  = 'REPLACE_ME_MODEL_CODE';
SET @badge_name  = 'REPLACE_ME_BADGE_NAME';
SET @product_url = 'REPLACE_ME_SONY_PRODUCT_URL';
SET @image_url   = 'REPLACE_ME_PROD_BLOB_IMAGE_URL';
SET @group_code  = 'telephoto-super-telephoto-lens';
SET @sort_order  = 1080;
SET @new_version = 'REPLACE_ME_YYYY-MM-DD-change-id-001';

-- 1) Preflight: group ต้องมีอยู่ และ model/code ต้องยังไม่ชน
SELECT *
FROM badge_display_groups
WHERE group_code = @group_code AND badge_type = 'product';

SELECT id, badge_code, product_model_code
FROM badge_rules
WHERE badge_code = CONCAT('product-', LOWER(@model_code))
   OR UPPER(product_model_code) = UPPER(@model_code);

-- 2) Parent rule; LAST_INSERT_ID(id) ทำให้ได้ id ทั้งกรณี insert และ rerun
INSERT INTO badge_rules (
  badge_code,
  badge_name,
  badge_type,
  rule_type,
  display_category,
  display_group,
  display_group_code,
  product_model_code,
  product_url,
  description,
  sort_order,
  is_active,
  active_from,
  active_to,
  registration_start,
  registration_end
)
VALUES (
  CONCAT('product-', LOWER(@model_code)),
  @badge_name,
  'product',
  'achievement',
  'Product Badge',
  @group_code,
  @group_code,
  @model_code,
  @product_url,
  CONCAT('Own ', @model_code),
  @sort_order,
  TRUE,
  NULL, NULL, NULL, NULL
)
ON DUPLICATE KEY UPDATE
  id = LAST_INSERT_ID(id),
  badge_name = VALUES(badge_name),
  product_model_code = VALUES(product_model_code),
  product_url = VALUES(product_url),
  description = VALUES(description),
  display_group = VALUES(display_group),
  display_group_code = VALUES(display_group_code),
  sort_order = VALUES(sort_order),
  is_active = TRUE;

SET @rule_id = LAST_INSERT_ID();

-- 3) หนึ่งรุ่น = achievement target 1
INSERT INTO badge_rule_thresholds (
  badge_rule_id,
  level,
  display_name,
  required_count,
  achieved_image_url,
  locked_image_url,
  share_image_url,
  sort_order
)
VALUES (
  @rule_id,
  'achievement',
  @badge_name,
  1,
  @image_url,
  NULL,
  @image_url,
  @sort_order
)
ON DUPLICATE KEY UPDATE
  display_name = VALUES(display_name),
  required_count = VALUES(required_count),
  achieved_image_url = VALUES(achieved_image_url),
  locked_image_url = VALUES(locked_image_url),
  share_image_url = VALUES(share_image_url),
  sort_order = VALUES(sort_order);

-- 4) SKU condition
INSERT INTO badge_rule_conditions (
  badge_rule_id,
  condition_label,
  match_type,
  required_count,
  sony_skus
)
VALUES (
  @rule_id,
  CONCAT('Own ', @model_code),
  'any',
  1,
  JSON_ARRAY(@model_code)
)
ON DUPLICATE KEY UPDATE
  match_type = VALUES(match_type),
  required_count = VALUES(required_count),
  sony_skus = VALUES(sony_skus);

-- 5) Bump version เพื่อ invalidate cache
INSERT INTO app_config (`key`, `value`)
VALUES ('badge_rules_version', @new_version)
ON DUPLICATE KEY UPDATE `value` = VALUES(`value`);

-- 6) Review ก่อน COMMIT
SELECT
  br.id,
  br.badge_code,
  br.product_model_code,
  br.display_group_code,
  brt.level,
  brt.required_count,
  brt.achieved_image_url,
  brc.match_type,
  brc.required_count AS condition_cap,
  brc.sony_skus
FROM badge_rules br
JOIN badge_rule_thresholds brt ON brt.badge_rule_id = br.id
JOIN badge_rule_conditions brc ON brc.badge_rule_id = br.id
WHERE br.id = @rule_id;

-- ผลถูกต้อง: COMMIT;
-- ผลไม่ถูกต้อง: ROLLBACK;
หลัง query review ต้องเลือกเอง COMMIT; หรือ ROLLBACK;. ตัวอย่างตั้งใจไม่ auto-commit เพื่อป้องกันการ paste แล้วเขียน PROD ทันที

-- Threshold ที่สูงกว่า condition caps: ต้อง review ทุก row ที่ได้
SELECT
  br.badge_code,
  MAX(brt.required_count) AS max_threshold,
  condition_caps.total_cap
FROM badge_rules br
JOIN badge_rule_thresholds brt ON brt.badge_rule_id = br.id
JOIN (
  SELECT
    badge_rule_id,
    SUM(
      CASE
        WHEN match_type = 'all' THEN JSON_LENGTH(sony_skus)
        ELSE required_count
      END
    ) AS total_cap
  FROM badge_rule_conditions
  GROUP BY badge_rule_id
) condition_caps ON condition_caps.badge_rule_id = br.id
GROUP BY br.id, br.badge_code, condition_caps.total_cap
HAVING MAX(brt.required_count) > condition_caps.total_cap;

Backup & Rollback Plan

วิธีสำรองและย้อนกลับข้อมูล หากพบปัญหา

Seed ทำงานในธุรกรรม: ถ้า script ล้มจะ rollback การเปลี่ยนแปลงรอบนั้น ถ้า commit แล้วแล้วพบว่ากฎผิด ต้องกู้จากสำเนาหรือ seed เวอร์ชันก่อนใน Git ไม่มี คำสั่ง rollback อัตโนมัติใน npm

สิ่งที่ seed ทำลายได้

  • แทนที่กลุ่มแสดงผลทั้งตาราง
  • ลบ thresholds/conditions ของกฎที่ถูก seed แล้วใส่ใหม่
  • ลบกฎที่ไม่อยู่ในไฟล์ seed (ลูกถูกลบด้วย ON DELETE CASCADE)
  • ไม่ลบ badge_calculation_logs
npm run db:reset DROP ตารางแอปทั้งหมดรวมปูมคำนวณ ห้ามใช้บน UAT/production

สำรองก่อนอัปเดต (Backup)

ใช้ mysqldump หรือเครื่องมือเทียบเท่าของ Azure ใส่โฮสต์/ผู้ใช้จากสภาพแวดล้อม ไม่ commit ไฟล์ที่มีรหัสผ่าน 

mysqldump --single-transaction --set-gtid-purged=OFF \
  -h <host> -P <port> -u <user> -p \
  --ssl-mode=REQUIRED \
  <database> \
  app_config badge_display_groups badge_rules \
  badge_rule_thresholds badge_rule_conditions \
  > badge-rules-backup-$(date +%Y%m%d-%H%M).sql

# ถ้าต้องการเก็บปูมคำนวณด้วย
mysqldump --single-transaction \
  -h <host> -P <port> -u <user> -p \
  --ssl-mode=REQUIRED \
  <database> badge_calculation_logs \
  > badge-calculation-logs-backup-$(date +%Y%m%d-%H%M).sql

จดควบคู่: Git SHA ของแอป, ไฟล์ seed ที่จะรัน (default หรือ prod), ค่า badge_rules_version ก่อนเปลี่ยน

สิ่งที่อยู่ในรีโป ใช้ย้อนฐานได้หรือไม่
scripts/db/seed-all-rules_backup.sql เป็น snapshot ของ generated SQL เก่า (รูป mock SVG) ไม่ใช่ dump ของ Azure ใช้ย้อน “ชุดกฎใน Git” ได้ถ้าตั้งใจกลับไปเวอร์ชันนั้น
scripts/db/uat_sony_table.sql dump อ้างอิง ณ วันที่ในไฟล์ ไม่รับประกันว่าตรงฐานปัจจุบัน
Git history ของ seed-data.mjs / prod/seed-data.mjs ย้อนโค้ดแล้วรัน db:seed / db:seed:prod ใหม่ จะเขียนทับกฎให้ตรงไฟล์นั้น

ย้อนกลับ (Rollback)

  1. หยุดการ seed ซ้ำถ้ายังไม่เสร็จ
  2. กู้จากไฟล์ dump ที่ถ่ายก่อนอัปเดต (restore เฉพาะตารางกฎ หรือทั้งฐานตามขอบเขตที่สำรอง)
  3. ทางเลือก: checkout ไฟล์ seed เวอร์ชันก่อน แล้ว npm run db:seed หรือ db:seed:prod — จะลบกฎที่เพิ่มในเวอร์ชันใหม่ถ้าไม่มีในไฟล์เก่า
  4. npm run db:verify ให้ตรงไฟล์ที่ใช้ย้อน
  5. ตรวจ badge_rules_version และเคสที่ยืนยันแล้ว (เช่น มี/ไม่มี product-sel1224gm) 
# ตัวอย่าง restore ตารางกฎ (ปรับตามเครื่องมือที่อนุญาต)
mysql --ssl-mode=REQUIRED -h <host> -P <port> -u <user> -p <database> \
  < badge-rules-backup-YYYYMMDD-HHMM.sql
ถ้า restore ทับตารางที่มี FK ให้ทำตามลำดับที่ dump กำหนด หรือปิดตรวจ FK ชั่วคราวเฉพาะหน้าต่าง restore ที่ควบคุมได้ อย่า seed ชุด default ทับ UAT ที่ต้องมี SEL1224GM เป็นเหรียญสินค้า

เมื่อ seed ล้มระหว่างรัน

seed.mjs เรียก beginTransaction และ rollback เมื่อ throw ฐานควรกลับไปสถานะก่อนคำสั่งนั้น จากนั้นแก้ข้อมูล seed หรือการเชื่อมต่อ แล้วยิงใหม่ ไม่ต้อง restore ถ้าธุรกรรมไม่ถูก commit

ไฟล์ SQL ที่ generate ใช้ START TRANSACTION / COMMIT การ import ที่ล้มครึ่งทางขึ้นกับไคลเอนต์ — ถ้าไม่แน่ใจให้ restore จาก dump

Schema rollback

migrate.mjs ไม่มี down migration คอลัมน์ที่เพิ่มแล้วจะไม่ถูกลบด้วยการรัน migrate ซ้ำ ถ้าต้องถอดคอลัมน์ ต้องมี ALTER ด้วยมือและแผนทดสอบแยก โดยทั่วไปการย้อนกฎไม่ต้องถอด schema
