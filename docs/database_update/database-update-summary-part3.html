Data Update Script / Migration Script

Script ที่ใช้ปรับปรุงข้อมูล พร้อม Version และวิธีใช้งาน

ไม่มีตาราง schema_migrations เวอร์ชันข้อมูลกฎอยู่ที่ app_config.badge_rules_version ค่าปัจจุบันใน seed ทั้งสองชุด: 2026-07-24-product-urls-001

เวอร์ชัน (Version)

ชั้น ที่เก็บ ค่าปัจจุบัน
Schema ลำดับ statement ใน scripts/db/migrate.mjs ไม่มีเลขเวอร์ชันในฐาน — รันซ้ำได้ (idempotent)
Badge rules scripts/db/seed-data.mjs และ scripts/db/prod/seed-data.mjs คีย์ badge_rules_version 2026-07-24-product-urls-001
สำเนา SQL เก่าในรีโป scripts/db/seed-all-rules_backup.sql 2026-07-20-confirmed-badge-rules-001 — ไม่ใช่แหล่งความจริง
เมื่อแก้กฎ ระดับ หรือเงื่อนไข ต้อง bump badge_rules_version ชุด default กับ prod ใช้สตริงเดียวกันทั้งที่แคตตาล็อกสินค้าต่างกันที่ SEL1224GM — อย่าใช้สตริงนี้แยกว่า seed ชุดไหนอยู่ในฐาน

รายการ script

คำสั่ง ไฟล์ สิ่งที่ทำ
npm run db:migrate scripts/db/migrate.mjs สร้างตาราง/คอลัมน์/index ALTER/INDEX ที่ซ้ำข้ามด้วย ER_DUP_FIELDNAME / ER_DUP_KEYNAME ไม่ลบแถว
npm run db:seed seed.mjs + seed-data.mjs ธุรกรรมเดียว: upsert app_config ลบแล้วใส่ badge_display_groups upsert กฎ แล้วแทนที่ thresholds/conditions ของกฎที่ seed ลบกฎที่ไม่อยู่ในไฟล์ (CASCADE ลูก)
npm run db:seed:prod seed.mjs --seed ./prod/seed-data.mjs เหมือน seed แต่ใช้ชุด UAT/prod (URL รูป blob, มีเหรียญ SEL1224GM)
npm run db:seed:all / :prod seed-all-rules.mjs migrate → seed → verify ติดกัน
npm run db:seed:sql generate-seed-sql.mjs เขียน seed-all-rules.sql จาก seed (ไม่แตะฐาน)
npm run db:seed:sql:prod generate + --out ./prod/seed-all-rules.sql สร้าง SQL ชุด prod — ไฟล์นี้ไม่ได้อยู่ในรีโปตอนจัดทำเอกสาร
npm run db:seed:sql:check generate-seed-sql.mjs --check CI บังคับให้ SQL ที่ commit ตรง seed เริ่มต้น
npm run db:verify / :prod verify.mjs เทียบ COUNT ตารางกับความยาวอาร์เรย์ใน seed และมีคีย์เวอร์ชัน
npm run db:reset reset.mjs DROP ตารางแอปทั้งหมดรวม badge_calculation_logs แล้ว migrate + seed ชุด default + verify — ใช้แค่ local
regenerate prod seed scripts/db/prod/generate-seed-data.mjs อ่าน dump uat_sony_table.sql ไม่รันใน CI

วิธีใช้งาน

ข้อกำหนด

  • DATABASE_URL รูปแบบ mysql://user:pass@host:port/db (ไม่มี secret ในเอกสารนี้)
  • Azure MySQL: DATABASE_SSL=true หรือ ?ssl=true — ไม่ปิดการตรวจใบรับรอง

Local — ใส่กฎชุด default

export DATABASE_URL='mysql://sony:sony@127.0.0.1:3307/sony_badges'
npm run db:migrate
npm run db:seed
npm run db:verify

หรือ npm run db:seed:all / ล้างทั้ง schema: npm run db:reset

อัปเดตกฎในโค้ดแล้วส่งเข้าฐาน

  1. แก้เฉพาะ scripts/db/seed-data.mjs (หรือ prod ตามสภาพแวดล้อม)
  2. bump badge_rules_version
  3. npm run db:seed:sql และ npm run db:seed:sql:check
  4. สำรองฐาน แล้ว npm run db:seed หรือ db:seed:prod
  5. npm run db:verify หรือ db:verify:prod

ทางเลือก SQL ด้วยมือ

npm run db:migrate
# แล้ว import scripts/db/seed-all-rules.sql (ชุด default)
npm run db:verify
Push แอปไป UAT ไม่รัน migrate/seed workflow ตรวจแค่ db:seed:sql:check กับเทส/lint/build ผู้ปฏิบัติการต้องรัน script ต่อ Azure MySQL จากโฮสต์ที่เข้าถึงได้

C. Schema ก่อน–หลัง migrate (idempotent)

ฐานว่าง: ได้ตารางครบตาม migrate.mjs รวมคอลัมน์ display_group_code, product_model_code, product_url, share_image_url และ index ที่ระบุ

ฐานที่มีตารางเก่าแล้ว: CREATE ข้ามถ้ามีอยู่ ALTER ที่ซ้ำถูกกลืน แถวข้อมูลเดิมไม่ถูกลบจนกว่าจะ seed

Seed ไม่แตะ badge_calculation_logs db:reset ลบตารางนี้ด้วย

วิธีเทียบบนฐานจริงหลังอัปเดต

  • ก่อนรัน: บันทึก SELECT value FROM app_config WHERE \`key\` = 'badge_rules_version' และ COUNT ของสี่ตารางกฎ
  • หลังรัน: npm run db:verify หรือ db:verify:prod ตามไฟล์ที่เพิ่ง seed
  • ตรวจว่ามีหรือไม่มี product-sel1224gm ให้ตรงชุดที่ตั้งใจ

Backup & Rollback Plan

วิธีสำรองและย้อนกลับข้อมูล หากพบปัญหา

Seed ทำงานในธุรกรรม: ถ้า script ล้มจะ rollback การเปลี่ยนแปลงรอบนั้น ถ้า commit แล้วแล้วพบว่ากฎผิด ต้องกู้จากสำเนาหรือ seed เวอร์ชันก่อนใน Git ไม่มี คำสั่ง rollback อัตโนมัติใน npm

สิ่งที่ seed ทำลายได้

  • แทนที่กลุ่มแสดงผลทั้งตาราง
  • ลบ thresholds/conditions ของกฎที่ถูก seed แล้วใส่ใหม่
  • ลบกฎที่ไม่อยู่ในไฟล์ seed (ลูกถูกลบด้วย ON DELETE CASCADE)
  • ไม่ลบ badge_calculation_logs
npm run db:reset DROP ตารางแอปทั้งหมดรวมปูมคำนวณ ห้ามใช้บน UAT/production

สำรองก่อนอัปเดต (Backup)

ใช้ mysqldump หรือเครื่องมือเทียบเท่าของ Azure ใส่โฮสต์/ผู้ใช้จากสภาพแวดล้อม ไม่ commit ไฟล์ที่มีรหัสผ่าน 

mysqldump --single-transaction --set-gtid-purged=OFF \
  -h <host> -P <port> -u <user> -p \
  --ssl-mode=REQUIRED \
  <database> \
  app_config badge_display_groups badge_rules \
  badge_rule_thresholds badge_rule_conditions \
  > badge-rules-backup-$(date +%Y%m%d-%H%M).sql

# ถ้าต้องการเก็บปูมคำนวณด้วย
mysqldump --single-transaction \
  -h <host> -P <port> -u <user> -p \
  --ssl-mode=REQUIRED \
  <database> badge_calculation_logs \
  > badge-calculation-logs-backup-$(date +%Y%m%d-%H%M).sql

จดควบคู่: Git SHA ของแอป, ไฟล์ seed ที่จะรัน (default หรือ prod), ค่า badge_rules_version ก่อนเปลี่ยน

สิ่งที่อยู่ในรีโป ใช้ย้อนฐานได้หรือไม่
scripts/db/seed-all-rules_backup.sql เป็น snapshot ของ generated SQL เก่า (รูป mock SVG) ไม่ใช่ dump ของ Azure ใช้ย้อน “ชุดกฎใน Git” ได้ถ้าตั้งใจกลับไปเวอร์ชันนั้น
scripts/db/uat_sony_table.sql dump อ้างอิง ณ วันที่ในไฟล์ ไม่รับประกันว่าตรงฐานปัจจุบัน
Git history ของ seed-data.mjs / prod/seed-data.mjs ย้อนโค้ดแล้วรัน db:seed / db:seed:prod ใหม่ จะเขียนทับกฎให้ตรงไฟล์นั้น

ย้อนกลับ (Rollback)

  1. หยุดการ seed ซ้ำถ้ายังไม่เสร็จ
  2. กู้จากไฟล์ dump ที่ถ่ายก่อนอัปเดต (restore เฉพาะตารางกฎ หรือทั้งฐานตามขอบเขตที่สำรอง)
  3. ทางเลือก: checkout ไฟล์ seed เวอร์ชันก่อน แล้ว npm run db:seed หรือ db:seed:prod — จะลบกฎที่เพิ่มในเวอร์ชันใหม่ถ้าไม่มีในไฟล์เก่า
  4. npm run db:verify ให้ตรงไฟล์ที่ใช้ย้อน
  5. ตรวจ badge_rules_version และเคสที่ยืนยันแล้ว (เช่น มี/ไม่มี product-sel1224gm) 
# ตัวอย่าง restore ตารางกฎ (ปรับตามเครื่องมือที่อนุญาต)
mysql --ssl-mode=REQUIRED -h <host> -P <port> -u <user> -p <database> \
  < badge-rules-backup-YYYYMMDD-HHMM.sql
ถ้า restore ทับตารางที่มี FK ให้ทำตามลำดับที่ dump กำหนด หรือปิดตรวจ FK ชั่วคราวเฉพาะหน้าต่าง restore ที่ควบคุมได้ อย่า seed ชุด default ทับ UAT ที่ต้องมี SEL1224GM เป็นเหรียญสินค้า

เมื่อ seed ล้มระหว่างรัน

seed.mjs เรียก beginTransaction และ rollback เมื่อ throw ฐานควรกลับไปสถานะก่อนคำสั่งนั้น จากนั้นแก้ข้อมูล seed หรือการเชื่อมต่อ แล้วยิงใหม่ ไม่ต้อง restore ถ้าธุรกรรมไม่ถูก commit

ไฟล์ SQL ที่ generate ใช้ START TRANSACTION / COMMIT การ import ที่ล้มครึ่งทางขึ้นกับไคลเอนต์ — ถ้าไม่แน่ใจให้ restore จาก dump

Schema rollback

migrate.mjs ไม่มี down migration คอลัมน์ที่เพิ่มแล้วจะไม่ถูกลบด้วยการรัน migrate ซ้ำ ถ้าต้องถอดคอลัมน์ ต้องมี ALTER ด้วยมือและแผนทดสอบแยก โดยทั่วไปการย้อนกฎไม่ต้องถอด schema
