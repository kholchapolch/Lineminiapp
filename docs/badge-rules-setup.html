Sony Badge Rules Setup Guide

เอกสารนี้อธิบายวิธีตั้งค่า Badge Shelf จากข้อมูลสินค้า Sony API โดยใช้ schema ปัจจุบัน: badge_rules, badge_rule_thresholds, และ badge_rule_conditions.

ภาพรวมการคำนวณ

1. Sony API products ส่งรายการสินค้าที่ลูกค้ามี เช่น model name, serial number, และ registration date. Sony ไม่ต้องส่ง Badge Shelf สำเร็จรูป.
2. Rule tables ระบบอ่าน Badge rules, thresholds, และ conditions จาก DB แล้ว match ด้วย SKU.
3. Badge Shelf แสดง Badge ทุกอันที่ลูกค้ารับได้: achieved เป็นสี, ยังไม่ได้เป็น dimmed.

Shelf Setup

Shelf ไม่ได้มาจาก JSON ของ Sony API. Shelf มาจาก rule ในระบบเรา แล้วเอา SKU จาก Sony API มาคำนวณว่าแต่ละ Badge achieved หรือยัง.

Current Sony APIM mapping: API ปัจจุบันส่ง prodDetails[].modelName แต่ยังไม่มี field SKU แยก. ดังนั้น badge_rule_conditions.sony_skus ต้องใส่ค่าที่ match กับ modelName แบบ normalized เช่น SEL70200GM2QSYX จนกว่า Sony จะเพิ่ม canonical SKU/model-code field.

Current DB Schema

3 ตารางหลักสำหรับตั้งค่า Badge
Table หน้าที่ Column สำคัญ
badge_rules ข้อมูลหลักของ Badge 1 rule badge_code, badge_name, badge_type, display_category, display_group, date window
badge_rule_thresholds ระดับที่แสดงบน Shelf. 1 rule มีหลาย level ได้ level, display_name, required_count, achieved_image_url, locked_image_url
badge_rule_conditions เงื่อนไขการ match SKU. 1 rule มีหลาย condition ได้ condition_label, match_type, required_count, sony_skus JSON
ทำไมไม่แยก condition item แล้ว: ลูกค้ามักส่ง requirement เป็น “rule + list of SKUs”. การเก็บ SKU list ใน badge_rule_conditions.sony_skus ทำให้ setup และ review ง่ายกว่า และ debug panel แสดง sony_sku_label_map เป็น object แบบ {"SKU": "label"} เพื่อเทียบด้วยตาได้เร็วขึ้น.

4 Rule Patterns ขั้นต่ำ

Pattern ที่ schema ปัจจุบันตั้งค่าได้
Pattern วิธีตั้งค่า ตัวอย่างใช้งาน
Any 1 in these SKUs match_type = 'any', required_count = 1 Own any key FF model
Min N in these SKUs match_type = 'min_count', required_count = N Own any 2 wildlife lenses from 5 SKUs
All required match_type = 'all'. ระบบใช้จำนวน SKU ใน list เป็น required ภายใน condition Own full GM trinity set
Level badge / Tier badge ใช้ condition เดียวหรือหลาย condition แล้วเพิ่มหลาย rows ใน badge_rule_thresholds Bronze = 1, Silver = 5, Gold = 10 หรือจะตั้ง 5 tiers ก็ได้

Any 1 vs Min 1 ต่างกันอย่างไร

ในผลลัพธ์พื้นฐาน any required_count 1 และ min_count required_count 1 สามารถให้ผลคล้ายกันได้ แต่ใช้สื่อความหมายต่างกัน.

แบบ ควรใช้เมื่อ อ่าน requirement แล้วรู้สึกอย่างไร
any ต้องการ “มีสัก 1 ตัวในกลุ่มนี้” และไม่คิดจะเพิ่มจำนวนขั้นต่ำ เหมาะกับ badge แบบ entry condition
min_count ต้องการ pattern ที่ขยายเป็น 2, 3, 5 ได้ หรือใช้กับ tier rule เหมาะกับ badge ที่นับจำนวนสินค้าเพื่อ progress

Complex Rules ที่ทำได้

Schema นี้ทำได้มากกว่า 4 pattern เพราะ 1 badge rule มีหลาย condition และหลาย threshold ได้. แต่ยังไม่ใช่ boolean expression engine แบบซ้อนอิสระทุกชั้น.

ตัวอย่างที่อธิบายกับลูกค้าได้
Rule Conditions Thresholds
Trinity Master Condition 1: any 1 from 16-35 GM family. Condition 2: any 1 from 24-70 GM family. Condition 3: any 1 from 70-200 GM family. Achievement = 3
All Rounder Condition 1: min_count 3 from 4 client-listed SKUs Achievement = 3
Body Collector Condition 1: min_count 10 from 10 body SKUs Bronze 1, Silver 5, Gold 10
Custom 5 Level Tier Condition 1: min_count 20 from campaign SKUs Level 1 = 1, Level 2 = 3, Level 3 = 5, Level 4 = 10, Level 5 = 20
Shared SKU Demo Same SKU can appear in Body, GM, and Creator Kit conditions Each rule calculates independently
ข้อควรระวัง: ถ้า client ต้องการ logic ซ้อนแบบ (A OR B) AND (C OR (D AND E)) ควรเปิด requirement ใหม่ เพราะ schema ปัจจุบันตั้งใจเป็น composed conditions แบบอ่านง่าย ไม่ใช่ full rule-expression engine.

ตัวอย่าง Code-Based Setup

ตอนนี้ default setup ใช้ MySQL และ seed จากไฟล์ scripts/db/seed-data.mjs เพื่อให้ review ได้ใน Git และไม่ต้อง paste SQL เข้า DB โดยตรง.

ความหมายของวันที่ในตัวอย่าง: registration_start/end คือช่วงวันที่จาก Sony product registeredAt ที่เอามาคิดสิทธิ์ Badge. ส่วน active_to = NULL แปลว่า Badge ยังอยู่บน Shelf หลังจบช่วง earn ได้ เพื่อให้ลูกค้าที่ qualify แล้วเห็น Badge ต่อไป.

Browser Cache และ Rules Version

หน้า Badge ใช้ browser localStorage เพื่อเก็บผลลัพธ์ Badge แบบ display-only. ไม่ใช้ cookie เพราะ cookie จะถูกส่งไปกับทุก request และเพิ่ม bandwidth โดยไม่จำเป็น.

Cache contract
ข้อมูล เก็บที่ไหน เหตุผล
skuHash Browser localStorage ใช้เช็คว่า Sony SKU set เปลี่ยนหรือยัง โดยไม่เก็บ raw SKU ใน browser cache
badge_rules_version app_config และ browser localStorage ถ้า rules version เปลี่ยน ระบบต้องคำนวณ Badge ใหม่
Badge result Browser localStorage ใช้แสดงผลเร็วเมื่อ server ยืนยันว่า customer, SKU hash, และ rules version ยังตรงกัน
Active rules Server memory cache + DB ลด DB bandwidth เพราะ rule config เปลี่ยนไม่บ่อย
ขั้นตอนเมื่อแก้ rule ใน DB: หลังแก้ badge_rules, badge_rule_thresholds, หรือ badge_rule_conditions ต้อง update app_config.badge_rules_version เพื่อบังคับให้ browser cache คำนวณใหม่.
